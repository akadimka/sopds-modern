# Архитектурный аудит sopds-modern (сентябрь 2026)

Комплексный анализ всего проекта: архитектура, логика кода, мёртвый/неиспользуемый код, безопасность, производительность, соответствие конвенциям репозитория (см. CLAUDE.md). Проведён параллельными агентами по 12 подсистемам. Для 10 подсистем каждая находка дополнительно проверялась отдельными агентами-скептиками (адверсариальная верификация, кроме severity=low); часть верификаций была прервана лимитом сессии — такие находки помечены как unverified-agent-error, но сама находка (от map-агента, с конкретными grep- и code-доказательствами) не отбрасывается, просто не получила дополнительного подтверждения скептиком. Для 2 подсистем (author/name pipeline, compiler+sync) — второй прогон после сброса лимита, без отдельного этапа верификации (помечены "single-agent"); самая значимая находка по компилятору/синхронизации (неэскейпленный XML при патче тегов автора/серии) перепроверена дополнительно вручную.

Это не баг-трекер в стиле docs/quality-roadmap.md — здесь нет обязательного регрессионного теста на каждый пункт. Это карта проблем для приоритизации будущей работы.

## Детали по подсистемам

### fb2parser_core: pipeline orchestrator + early passes (filename/structural)

This subsystem is the entry point and earliest stages of fb2parser_core's heuristic 6-pass FB2-library-organizing pipeline. `RegenCSVService.regenerate()` (src/fb2parser_core/regen_csv.py) — invoked from fb2parser_web and from the CLI (`python regen_csv.py`) — walks a folder of FB2 files and writes regen.csv with a best-guess author/series/genre per file. Data flow: Precache builds a folder→author cache once; `Pass1ReadFiles` then reads every FB2 file in parallel via ProcessPoolExecutor, combining that cache with per-file SAX-parsed metadata into `BookRecord`s; `Pass2Filename`/`Pass2Fallback` extract authors from filenames/metadata for records the folder cache missed; and a large inline "SERIES extraction from folders" block plus two structurally parallel PASS0/1/2 mini-frameworks (`folder_author_parser`, genuinely used; `folder_series_parser`, dead) resolve per-file series before handing off to normalization/consensus passes and roughly 30 sequential `_postcheck_*` corrections. Design quality is uneven: the low-level analyzers (`file_structural_analysis.py`, `folder_author_parser`) are reasonably self-contained and testable, but `regen_csv.py` itself has grown into a single 3,195-line God Object (`RegenCSVService`, 42 methods, 29 of them `_postcheck_*`) whose correctness depends on a fixed, comment-documented order of dozens of small heuristic patches, each traceable to one specific real-world library layout the maintainer hit. That growth history has left behind an unused parallel series-parsing module, a dead duplicate of the folder-author-walk logic, a duplicated-and-diverged series heuristic across two files, and a hardcoded personal-file debug scan left running in the shipped pipeline. No SQL injection, unsafe deserialization, XXE, subprocess, or credential-handling issues were found within this specific subsystem's files — its main risks are maintainability/fragility (the postcheck chain) and a handful of confirmed dead-code paths rather than classic security vulnerabilities.</summary>

### fb2parser_core: consensus/normalize passes (contains the single largest file in the repo)

This subsystem is the heuristic "brain" of fb2parser_core's regen_csv pipeline: given a raw list of BookRecord objects (already carrying FB2 metadata from Pass 1), it decides each book's final proposed_series and proposed_author by cross-referencing folder structure, filename patterns and FB2 metadata, then reconciles disagreements across sibling files. It is invoked strictly in sequence from regen_csv.py: Pass2SeriesFilename (series from filenames/folders) -> Pass3SeriesNormalize (series name cleanup) -> Pass3Normalize (author name normalization) -> Pass4Consensus (folder/series/author consensus voting) -> Pass5Conversions (re-apply surname conversions) -> Pass6Abbreviations (expand abbreviated author names). Data flows through the same mutable `records: List[BookRecord]` at every stage, with each pass mutating fields in place and later passes trusting earlier ones' `*_source` provenance tags to decide what they're allowed to override. Design quality is a mixed picture: the pipeline concept (provenance-tagged incremental refinement with a documented regression-fixture process per edge case) is sound and the project clearly invests in guarding against regressions, but the two largest files (pass2_series_filename.py at 5427 lines, and pass4_consensus.py whose execute() is a single ~1840-line method) have grown by pure accretion - one heuristic regex rule per historical bug, with no shared abstraction, some outright duplicated logic, a handful of genuinely dead methods, and at least one broad silent exception handler. No security-relevant sinks (SQL, subprocess, XML parsing, network I/O) exist in these six files - the risk here is entirely maintainability and correctness-through-heuristic-drift, not injection/traversal/etc.

### fb2parser_core: author/name extraction and normalization

This subsystem is fb2parser_core's author-name pipeline: extracting a proposed author from folder structure/filename/FB2 metadata and normalizing it to "Фамилия Имя" form, plus a Wikidata-based gender lookup used by the web UI. It has two disjoint faces. The first is a large, entirely unreachable "priority resolution" engine (FB2AuthorExtractor.resolve_author_by_priority and ~25 supporting methods, plus all of author_processor.py and author_utils.py) that nothing in the live pipeline calls - the real entry points into fb2_author_extractor.py are only _extract_all_metadata_at_once() (called once per file from pass1_read_files.py) and _extract_genres_from_fb2() (called from genre_scan_service.py). The second is the genuinely live normalization stack - name_normalizer.AuthorName (word-order/particle/patronymic heuristics) driven through author_normalizer_extended.AuthorNormalizer, consumed by PASS 3/4/5/6 - plus block_level_pattern_matcher.py (used by PASS 2) and gender_lookup.GenderLookupService (used by the web UI). Design quality is uneven: the live normalization logic is sophisticated and well-commented but has essentially no direct unit tests, while roughly 85% of the subsystem's largest file is dead scaffolding left over from an abandoned ExtractionResult/priority-based redesign, duplicated in several other files in this set.

### fb2parser_core: series/genre resolution + FB2 SAX extraction of untrusted files

This subsystem extracts author/series/genre facts from untrusted FB2 XML files (via stdlib SAX/expat) and resolves them against the user's genre taxonomy and series/author heuristics. It is entered per-file from fb2parser_core's 6-pass regen_csv pipeline (pass1_read_files.py instantiates FB2SAXExtractor or the parallel FB2AuthorExtractor and calls only `_extract_all_metadata_at_once()`), while SeriesProcessor/SeriesNormalizer/series_helpers post-process that raw metadata together with filename/folder heuristics in later passes, and GenresManager/genre_assign/genre_scan_service form a separate path that maps raw `<genre>` codes to a taxonomy (genres.xml) and rewrites `<genre>` tags in FB2 files in place via regex. Data flows one-directionally: disk bytes (FB2 or FB2.ZIP) → SAX-extracted facts → heuristic normalization/consensus passes → CSV / genres.xml, with per-file try/except isolation so most operations survive a single malformed file. Design quality is uneven: a large majority of FB2SAXExtractor is an abandoned, fully duplicated author-resolution engine that the live pipeline never calls (a sibling class, FB2AuthorExtractor, does the real work), the series-consensus normalization regex is copy-pasted and independently maintained in two files with an explicit "duplicate logic" comment acknowledging the risk, and the zip/decompression paths (shared by hashing, sync, and compilation) have no protection against oversized/zip-bomb `.fb2.zip` archives despite handling files whose origin is not controlled. XML entity-expansion safety currently rests entirely on implicit stdlib/expat defaults rather than anything asserted in code.

### fb2parser_core: settings/logging/metadata-cache infrastructure

This subsystem provides cross-cutting infrastructure the fb2parser_core pipeline depends on. SettingsManager persists user/machine configuration to two JSON files (app_settings.json committed, config.json gitignored) behind ~60 typed accessor methods; Logger is a bounded in-memory ring buffer for progress strings; MetadataCache is a per-file SQLite (WAL) cache keyed by path+mtime+hash that lets PASS 1 skip re-parsing unchanged FB2 files, self-invalidating when the parser's own source files change; Precache is a one-time folder-tree walk before PASS 1 that classifies folders as author/series/genre/collection and memoizes the result for every PASS 1 worker. ### fb2parser_web: Django views/routes for the library-organizer UI

fb2parser_web is the Django UI layer for sopds-modern's vendored FB2-library organizer: one urls.py (76 routes) dispatches into a single ~3016-line views.py that renders htmx-driven dashboard/scan/normalize/compiler/sync/settings pages plus JSON/HTML-fragment endpoints for their controls, entered exclusively via `/fb2parser/...` mounted with a plain `include()` in sopds/urls/base.py (no blanket auth wrapper — every view is individually responsible for its own `@staff_member_required`). ### opds_catalog: OPDS feed serving, downloads, scanner (external-facing HTTP surface)

opds_catalog is the public-facing OPDS server: feeds.py (Django syndication Feed subclasses wrapping opdsFeed/Atom1Feed) exposes navigation/search feeds for catalogs, authors, series, genres and books; dl.py serves the actual binary content (download, cover/thumbnail extraction, in-browser HTML reading, format conversion); opdsdb.py/sopdscan.py implement the filesystem-to-DB scanner invoked by the sopds_scanner management command (cron-scheduled via APScheduler or run once); sopds_config.py is a settings proxy fronting a JSON config file. Requests enter via urls.py, which wires raw regex URL params almost directly into Feed.get_object()/view functions; querying goes exclusively through Django ORM (via a services/ layer for authors/books/series/genres/catalogs), so classic SQL-injection risk is essentially absent — the real exposure is at the edges: authentication is enforced only where a view/Feed explicitly opts into the sopds_auth_validate decorator, several download/read endpoints in dl.py were never wired to it, one endpoint builds filesystem paths from data that ultimately originates in scanned book files (ZIP entry names, FB2 titles) without sanitization, and the FB2 XML parser used for cover/metadata extraction has no XXE hardening. Architecturally the design is reasonably layered (feeds → services → ORM) but has some real inconsistencies: a config-access layer with zero caching that's hit dozens of times per request, a pagination helper that materializes whole catalog folders in Python before slicing, a user-facing "logical delete" setting whose implementation was silently commented out, and a per-request dynamic module load for the FB2-to-HTML reader. Overall: solid ORM discipline, but the HTTP-facing auth model is inconsistently applied and a few performance/data-integrity foot-guns exist that would bite on a large or adversarially-seeded library.

### opds_catalog: models, service layer, external rating fetchers, management commands

This subsystem is the OPDS-facing data/service layer of sopds-modern: opds_catalog/models.py defines the book/author/genre/series/catalog schema and the ratings side-tables (Samlib/AuthorToday/Fantlab/Litmarket), the services/*.py modules wrap query-building (search, pagination, counters) used by both feeds.py (OPDS) and sopds_web_backend's views, and inpx_parser.py/fb2parse.py feed the scanner (sopdscan.py) that populates the DB from either a filesystem walk or an imported INPX archive. ### book_tools: FB2/EPUB/MOBI parsers for untrusted user files

book_tools is the shared library that turns an uploaded or scanned FB2/EPUB/MOBI file into catalog metadata (title, authors, series, genres, cover) for the OPDS catalog's scanner (opds_catalog.sopdscan) and download/cover views (opds_catalog.dl), and it treats every file it parses as untrusted, internet-sourced content. Its production entry points are book_tools.format.create_bookfile()/create_bookfile_service() (mimetype sniffing via mime_detector.py, then dispatch through a small function-based registry in services.py) plus, for FB2 covers specifically, a direct call into format/parsers.py's FB2 class from dl.py. Internally the subsystem carries three overlapping generations of parser code — an original BookFile-subclass-per-format design (format/fb2.py, format/epub.py, format/mobi.py over pymobi/), an expat-SAX FB2 variant (fb2sax.py), and a newer DTO/EbookMetaParser design (format/parsers.py, format/ebook_parsers/) — and production wires together an inconsistent subset of these (parsers.FB2 for FB2, but the older epub.py EPub for EPUB, pymobi.mobi.BookMobi directly for MOBI metadata), leaving several fully-built, tested alternatives (EpubParser, ParserFactory/EbookParser, format/fb2.py) unused in production. That unfinished migration is the root cause of the subsystem's worst bug: the generic create_bookfile() path used for cover extraction on every non-FB2 format returns a plain BookFile whose cover methods are no-ops, so EPUB/MOBI/DJVU/PDF covers never actually render. Layered on top of that architecture drift, none of the several lxml XML-parsing call sites handling attacker-supplied FB2/EPUB XML configure safe entity resolution (XXE exposure), and a meaningful slice of legacy functionality (EPub's fake DRM encryption, MOBI decompression for non-PalmDOC types) is either fully dead or would crash if ever exercised again. The mimetype-detection layer (mime_detector.py) and the core FB2 XPath metadata extraction are, by contrast, solid, well-bounded and reasonably tested — the risk here is concentrated in the format-parser layer's incomplete refactor rather than the subsystem as a whole.

### Django project config: settings, urls, WSGI/ASGI, deployment security posture

This subsystem is the Django project's plumbing layer: three settings modules built on django-environ's FileAwareEnv (base.py for shared/production config, local.py layering in debug_toolbar + LocMemCache for dev, test.py layering in LocMemCache + a tmp sqlite DB for CI), three matching URLconf variants, stock wsgi.py/asgi.py entrypoints, and gunicorn.py as the actual production process config. **[Низкая | корректность] INTERNAL_IPS gateway-guess strips the wrong number of characters**

- Файл: `src/sopds/settings/local.py:29`
- `ip = socket.gethostbyname(socket.gethostname()); INTERNAL_IPS += [ip[:-1] + "1"]` is meant to add the host's gateway address (typically `x.x.x.1`) to INTERNAL_IPS so django-debug-toolbar/the debug context processor recognize requests coming through it (e.g. from a Docker bridge). `ip[:-1]` strips only the last *character* of the IP string, not the last octet. This only happens to produce a correct `...1` address when the resolved IP's last octet is a single digit (e.g. `172.17.0.2` → `172.17.0.1`); for the common case of a multi-digit last octet (e.g. `192.168.1.132`), it produces `192.168.1.131` — the wrong address entirely — so the intended gateway never actually lands in INTERNAL_IPS. Dev-only impact (DEBUG is always True here), no production exposure.
- Доказательство: src/sopds/settings/local.py:28-29; for ip="192.168.1.132", ip[:-1]+"1" == "192.168.1.131", not the gateway "192.168.1.1".
