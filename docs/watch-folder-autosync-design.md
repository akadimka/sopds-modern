# Автосинхронизация папки наблюдения — дизайн

Статус: согласовано с пользователем, реализация по этапам (см. конец).
Первый черновик идеи — 2026-08-04; этот документ его заменяет (2026-10-05).

## Цель

Скачанные папки с книгами попадают в **папку наблюдения**. Проект сам
определяет автора, серию и жанр, раскладывает книги в библиотеку и
сообщает о результате. Человек нужен только там, где программа не
уверена — и такие места она явно отдаёт ему, а не угадывает.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Включение | Опция в настройках + путь к папке наблюдения + режим |
| Когда работает | Не в реальном времени, а первым шагом **планового скана** библиотеки: сначала обработка папки наблюдения, затем обычный скан (он подхватит новые книги) |
| Уведомления | Telegram: новинки — в **канал**; админу — в личный чат: нерешённые порции, коллизии, сбои |
| Исходники после автообработки | **Удаляются** (как при ручной синхронизации); не прошедшее автообработку остаётся в папке наблюдения |
| Тег `<genre>` | **Переписывается** выбранным жанром (как при ручном назначении) |
| Где работает | Сервер (`sopds-scan.service`); локально — для тестирования |

## Как это встраивается в существующий процесс

Ручной процесс сейчас: «Скан жанров» → человек назначает жанр папке
(`GenreAssignmentService` переписывает `<genre>`) → «Синхронизация»
выбранных папок (`SynchronizationService.synchronize(allowed_folders=…)`)
→ автокомпиляция по затронутым авторам.

Автосинхронизация **заменяет человека только на шаге назначения жанра**.
Всё остальное — тот же проверенный код синхронизации и компиляции:

```
плановый запуск sopds_scanner
 └─ autosync (если включён)
     1. найти порции = подпапки верхнего уровня папки наблюдения
     2. пропустить «ещё качающиеся» (.part/.!qB, mtime моложе 30 мин)
     3. regen по порции → автор/серия/номер/коды/издательская серия
     4. голосование по жанру (см. ниже) → решение по каждой единице
     5. уверенные единицы: переписать <genre>, synchronize(allowed_folders),
        автокомпиляция; журнал
     6. неуверенные: остаются на месте → «Входящие» + сообщение админу
     7. сводка новинок → Telegram-канал
 └─ обычный скан библиотеки (scan_all)
```

Синхронизация и скан выполняются в одном процессе последовательно —
гонки между ними нет. С ручной синхронизацией из веб-интерфейса
(другой процесс) — общая файловая блокировка.

## Голосование по жанру

Проверено на библиотеке пользователя (4991 книга, эталон — папка жанра;
скрипты прототипа и цифры — в истории обсуждения 2026-10-05).

**Единица решения.** Серия внутри порции (все её тома вместе); книга
без серии — сама по себе. Порция целиком добавляет общий голос: в
реальной библиотеке 98.6% книг лежат в главном жанре своей порции.

**Сигналы и веса.**

| Сигнал | Вес | Условие |
|---|---|---|
| Серия автора уже есть в библиотеке | 10 × доля жанра | — |
| Издательская серия (`publish-info/sequence`) | 6 | ≥3 книг в библиотеке, ≥80% в одном жанре |
| Коды `<genre>` | 4 × доля «знакомых» кодов | код → жанр: выученное из библиотеки (≥5 книг), иначе `GenresManager.resolve_code` (справочник/`genres.xml`); тег, уже содержащий имя жанра, — голос за этот жанр |
| Профиль автора | 3 × доля жанра | только если у автора ≥5 книг **и** коды молчат или противоречат друг другу |
| Порция целиком | 6 × доля × сила | только если сильные сигналы порции согласны на ≥60%; профиль в общий голос порции не входит |

**Решение «автоматически»** — все условия сразу:
1. доля победителя ≥ порога (по умолчанию 80%);
2. у победителя ≥ 3 баллов;
3. есть **якорь** (серия, издательская серия или профиль автора) **или**
   **надёжный код**: выученное правило «код → жанр», подтверждённое
   ≥3 разными порциями с чистотой ≥90%, указывает на победителя, и ни
   один надёжный код не указывает на другой жанр.

Иначе — «Входящие» с предвыбранной подсказкой.

**Почему именно так (что показала проверка).**
- Без п.3 автоматика разгоняет ошибки через память: первая порция
  детективов, пришедшая до того, как детективы появились в памяти,
  уходила в Фантастику, и дальше память «училась» на этой ошибке
  (19–35% ошибок при сборке библиотеки с нуля). С п.3 — ~1%.
- Профиль автора по 2 книгам уводил целую серию в чужой жанр — отсюда
  минимум 5 книг и запрет усиливать профиль голосом порции.
- «Тонкие» жанры пользователя (Остросюжетный детектив / Триллер /
  Детектив / Приключения / Политический боевик) — выбор по издательской
  серии, кодами не различаются. Первая порция такой серии всегда идёт
  человеку; дальше её подхватывает память (якорь «издательская серия»).

Итог проверки: новая книга/том известного — ~85% автоматически при
~1.5% ошибок; новая незнакомая порция — ~30% автоматически при 0.7%
ошибок; решений человека на 93 порциях — 78–85 вместо 104 сегодня.

## Память (индекс знаний)

Файл `src/fb2_data/settings/library_memory.db` (SQLite, машинно-локальный,
в `.gitignore` — как `metadata_cache.db`).

- `books` — индекс библиотеки: путь, размер, mtime, **отпечаток текста**
  (SHA1 нормализованного фрагмента `<body>`), жанр/автор/серия из пути
  `Жанр/Автор/[…/]Серия/файл`, издательские серии. Обновляется
  инкрементально (новые/изменённые/удалённые файлы) перед каждым запуском.
- `orig_codes` — **исходные** коды `<genre>` по отпечатку, порция-источник,
  кем решено (человек/авто). Пишется ДО того, как тег будет переписан —
  и при ручном назначении жанра, и при автосинхронизации. Отпечаток
  `<body>` не меняется при переписывании описания и перемещении файла —
  так книга библиотеки связывается со своими исходными кодами.
  Существующая библиотека исходных кодов не хранит: их можно один раз
  восстановить командой `autosync_bootstrap --sources <папка исходников>`
  (локально — Test2), иначе память кодов набирается по ходу работы, а
  якоря серий/авторов работают сразу.

Из этих двух таблиц строятся словари голосования: серия → жанр,
автор → профиль, издательская серия → жанр, код → жанр (+ по порциям).

## Настройки (`config.json`, раздел `autosync`; машинно-локальные)

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `mode` | `off` | `off` / `dry_run` (только отчёт, ничего не трогает) / `auto` |
| `watch_folder` | — | папка наблюдения (в UI — кнопка «Обзор») |
| `confidence` | 0.8 | порог доли победителя |
| `quiet_minutes` | 30 | порция с файлами моложе — ждёт следующего запуска |
| `telegram_token` | — | токен бота |
| `telegram_channel` | — | канал новинок (`@name` или id) |
| `telegram_admin_chat` | — | личный чат админа |
| `telegram_proxy` | — | на случай закрытого `api.telegram.org` |
| `public_url` | — | базовый адрес сайта для ссылок в сообщениях |

Страница настроек — рядом с расписанием скана (`sopds_settings.html`);
там же кнопка «Обработать сейчас».

## «Входящие» и журнал

- **Входящие** (`/fb2parser/inbox/`): порции/единицы, не решённые
  автоматически: подсказка, причины, кнопка «Подтвердить для всей
  порции» или выбор жанра. Решение = назначение жанра + синхронизация
  этой порции сразу, не дожидаясь расписания; решение пишется в память
  (`orig_codes`, решено человеком).
- Сюда же — всё, что синхронизация уже умеет откладывать: ручная сверка
  автора (`reconciliation_notes`), конфликт жанра серии
  (`genre_conflict_notes`), битые файлы.
- **Журнал** (`library_memory.db`, таблица `autosync_log`): по каждой
  порции — время, режим, что куда перемещено, жанр и причины, итог.
  Откат порции = вернуть её файлы из библиотеки в папку наблюдения как
  новую порцию с пометкой «на ручное решение».

## Telegram

Этап 1 — **только отправка** из плановой задачи через Bot API (никакого
постоянного процесса):
- **канал**: одна сводка за запуск — новые книги, сгруппированные по
  жанру → автору → серии, со ссылками на страницы книг;
- **админ**: итог запуска (сколько разложено, сколько ждёт решения и
  почему, ссылка на «Входящие»); отдельное сообщение при сбое запуска.

Этап 2 — **кнопки решений** у админа («Фантастика / Детектив / Во
Входящие»): отдельный systemd-сервис бота в режиме long polling — не
требует HTTPS и входящих подключений. Команды принимаются только из
`telegram_admin_chat`.

Токен — только в `config.json` (не в git). Перед включением на сервере
проверить доступ к `api.telegram.org`.

## Этапы реализации

1. ✅ **Ядро**: `library_memory.py` (индекс + `orig_codes`), `genre_voting.py`
   (сигналы, политика), запись исходных кодов при ручном назначении жанра,
   команды `autosync_bootstrap` и `autosync --dry-run <папка>` (текстовый
   отчёт «что бы я сделал»). Тесты.
2. ✅ **Автосинхронизация**: `AutosyncService.run()` (порции, тишина,
   голосование → назначение жанра → `synchronize(hold_files=…)` →
   автокомпиляция → журнал `autosync_runs`/`autosync_books`), раздел
   настроек (вкладка «Расписание», только суперпользователь, папка не может
   пересекаться с библиотекой), файловая блокировка `sync_lock` с ручной
   синхронизацией, шаг в `sopds_scanner.scan()` перед `scan_all`, команда
   `manage.py autosync` (по режиму). Попутно: назначение жанра теперь
   работает с `.fb2.zip` (раньше папкой — пропускались, файлом — архив
   затирался XML) и не удваивает `\r` на Windows.
3. **UI**: кнопка «Обработать сейчас», страница «Входящие» (спорные книги
   последнего запуска из журнала; решение = назначение жанра + синхронизация
   порции).
4. **Telegram, отправка**: канал + админ. Внимание: путь книги в журнале —
   место сразу после перемещения; автокомпиляция затем собирает тома серии
   в один файл, так что ссылки на книги в сводке надо искать в каталоге по
   автору/серии/названию уже после скана, а не по этому пути.
5. **Telegram, кнопки** решений для админа.

Каждый этап — отдельный коммит после тестов; поведение по умолчанию
(`mode = off`) не меняет ничего в существующей работе.
