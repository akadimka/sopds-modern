# Второй сервер (sopds-modern-2) — статус

> Адрес, порты, имена пользователей и SSH-ключ здесь заменены плейсхолдерами —
> репозиторий публичный. Реальные значения хранятся локально, вне репозитория.

Второй, независимый экземпляр sopds-modern (своя библиотека, не связана с
основным сервером `sopds-modern`/turnkey). Развёрнут по `DEPLOY.md` с
поправками под Debian 13 (trixie) вместо Debian 11/TurnKey 17.

**Сервер:** `<SERVER_IP>` за роутером MikroTik (RouterOS), внутренний адрес
`<INTERNAL_IP>`. SSH: внешний порт `<SSH_PORT>` проброшен на 22. SSH-алиас
`sopds-modern-2` в `~/.ssh/config`.

**Пользователи** (с 2026-10-07):

- `<ADMIN_USER>` — только вход по SSH (по ключу), **без sudo** (убран из
  группы `sudo`).
- `root` — администрирование: `su -` с паролем root из сессии
  `<ADMIN_USER>`. Прямой вход root по SSH закрыт в sshd.

Без терминала (из скриптов) `su` принимает пароль через stdin; не
используйте для этого `ssh -tt` — пароль попадёт в вывод эхом.

Секреты (SSH-пароли, пароль суперпользователя Django) в этот файл
**намеренно не записаны**. Пароль суперпользователя стоит сменить после
первого входа.

## Доступ: только с российских адресов

Сервер (или сеть провайдера) принимает подключения только с российских
IP. Рабочий ПК выходит в интернет через зарубежный VPN — с него подключение
просто зависает по таймауту, как будто сервер выключен; с телефона
(российский IP) всё работает.

Поэтому в `~/.ssh/config` для `sopds-modern-2` указан
`ProxyJump sopds-modern` — соединение идёт через основной сервер, который
выходит в интернет через российского провайдера. Ключ остаётся на ПК.

> 2026-09-23 это было ошибочно принято за блокировку после `ufw enable`.
> На деле сервер всё это время работал (18 дней без перезагрузки на
> 2026-10-07), ufw настроен верно.

## Публикация: `https://<DOMAIN>` через прокси админов (2026-10-09)

Сайт открывается по доменному имени. DNS домена указывает на другой
внешний адрес, чем SSH: там стоит обратный прокси админов (openresty,
виртуальная машина `<PROXY_IP>` в той же локальной сети). Прокси принимает
`http`/`https` для домена, сам держит действительный сертификат и пересылает
запросы на порт 80 нашего сервера по HTTP с заголовком `X-Forwarded-Proto`.

- Apache `:80` (`ServerName <DOMAIN>`) отдаёт сайт (прокси на
  `127.0.0.1:8008`) — без редиректа — и пускает только `<PROXY_IP>` и
  `127.0.0.1`: иначе любой из локальной сети мог бы подделать
  `X-Forwarded-Proto` и выдать HTTP за HTTPS.
- Django остаётся в HTTPS-режиме: `http://<DOMAIN>` → 301 на
  `https://<DOMAIN>/` (по заголовку Host), cookies с флагом `Secure`.
- Внешний IP напрямую на порту 80 — это веб-интерфейс самого роутера
  (RouterOS), а не сайт.

> Раньше на `:80` стоял `Redirect permanent / https://<SERVER_IP>/` —
> на внешний адрес, 443 которого снаружи не проброшен; сайт через прокси
> из-за этого не открывался. Бэкап старых `.env` и конфига Apache —
> в `/root/backup-20261009-*` на сервере.

Снаружи проверено: `http://` → `https://`, `/web/login/` 200, вход с
неверным паролем отклоняется (CSRF проходит), OPDS 401 без авторизации,
статика 200.
