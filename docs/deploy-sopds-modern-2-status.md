# Развёртывание второго сервера (sopds-modern-2) — статус

Второй, независимый экземпляр sopds-modern (отдельная библиотека, не
связанная с основным сервером `sopds-modern`/turnkey). Разворачивается по
`DEPLOY.md` с поправками под Debian 13 (trixie) вместо Debian 11/TurnKey 17.

**Сервер:** `37.18.255.71`, SSH-порт `8801`, пользователь `lama-admin`
(добавлен в группу `sudo`; изначально не имел прав sudo). SSH-алиас
`sopds-modern-2` в `~/.ssh/config` (отдельный ключ `id_ed25519_sopds2`).

Секреты (SSH-пароли, пароль root, пароль суперпользователя Django) в этот
файл **намеренно не записаны** — они были переданы в чате и должны быть
сохранены в менеджере паролей; пароль суперпользователя стоит сменить
после первого входа.

## Сделано

- Пакеты: git, build-essential, memcached, apache2, calibre, ufw — установлены
  (пути `apache2`/`ufw` в `/usr/sbin`, не в PATH обычного пользователя).
- `uv` установлен в `/usr/local/bin` (доступен всем, не только root).
- Python 3.13.15 установлен через `uv python install 3.13`
  (`UV_PYTHON_INSTALL_DIR=/opt/uv/python`).
- Репозиторий склонирован в `/opt/sopds-modern` (HEAD на момент установки:
  `3ae8acb`), `uv sync --no-dev` выполнен.
- `.env` (`/opt/sopds-modern/src/.env`):
  - `SOPDS_DB_ENGINE=sqlite` (отдельная, независимая библиотека — Postgres
    не нужен)
  - `SOPDS_BOOK_PATH=/srv/sopds-books` (создана, пока пустая — файлы книг
    заливаются позже)
  - `ALLOWED_HOSTS=37.18.255.71,localhost,127.0.0.1`
  - `SOPDS_USE_HTTPS=True` + `SOPDS_TRUST_X_FORWARDED_PROTO=True` — уже
    готовый механизм в `sopds/settings/base.py` (баг №98), включён под
    TLS-терминацию на Apache перед gunicorn.
- `secret_key.txt` сгенерирован, `chmod 600`.
- Миграции применены, суперпользователь `admin` создан.
- systemd-сервис `sopds-modern` (gunicorn) — установлен, enabled, запущен,
  слушает `127.0.0.1:8008` (локально отвечает, `curl` подтверждён).
- Apache: самоподписанный сертификат (`/etc/ssl/sopds-modern/`, 10 лет),
  `sites-available/sopds-modern.conf` — reverse-proxy 443→127.0.0.1:8008,
  редирект 80→443, модули `proxy proxy_http headers ssl` включены,
  `000-default` отключён. `apache2ctl configtest` — OK, сервис запущен.
- `ufw` включён: `allow 8801/tcp` (SSH), `allow 80/tcp`, `allow 443/tcp`,
  `default deny incoming` — до включения проверено, что правило для
  SSH-порта уже есть (чтобы не заблокировать себя).

## Проблема — сервер недоступен снаружи

Сразу после `ufw enable` сервер перестал отвечать **на всех портах**
(8801/SSH, 80, 443) — не только на тех, что не были явно разрешены.
Подключение зависает (`Connection timed out`), а не отклоняется
(`Connection refused`) — характерно для блокировки на файрволе/роутере, а
не для упавшего сервиса. Собственное интернет-соединение проверено
отдельно (доступ к 8.8.8.8 работает) — проблема именно в маршруте до
`37.18.255.71`.

**Рабочая версия пользователя:** на роутере проброшен только SSH-порт
(8801), проброса для 80/443 нет — это объясняет их недоступность, но не
объясняет, почему именно в этот момент перестал отвечать и сам SSH
(8801), который до этого работал.

## Что нужно, чтобы продолжить

1. **Проброс портов на роутере** на внутренний IP этого сервера:
   `80/tcp`, `443/tcp` — для сайта; **перепроверить `8801/tcp`** (SSH) —
   был рабочим, сейчас недоступен.
2. Если после проброса портов SSH всё равно не отвечает снаружи — нужен
   **локальный/консольный доступ** к серверу (не по сети), чтобы
   выполнить `sudo ufw disable` — на случай, если дело в самом ufw, а не
   в роутере. После восстановления доступа правила ufw нужно будет
   перепроверить/переналожить аккуратно (allow SSH-порт → allow 80/443 →
   только потом снова `ufw enable`).
