## 2. Убрать недетерминизм многопроцессности — ✅ Готово

`Pass1ReadFiles.execute()` собирал `records` в порядке ЗАВЕРШЕНИЯ
воркеров (`concurrent.futures.as_completed`), а не в стабильном
порядке — из-за чего последующий консенсус (порядок слов в имени
автора, дробные номера подсерий типа "2.1"/"2.2", капитализация серий)
иногда давал разные результаты между прогонами без изменения кода.

Фикс: `records.sort(key=lambda r: str(r.file_path))` сразу после сбора
результатов в `pass1_read_files.py`. Проверено на полной библиотеке
Test1 (~12000 файлов): два подряд прогона одинакового кода дали
**0 расхождений** (было — десятки на каждую пару прогонов). Diff
против baseline (без фикса) — 172 записи, все относятся к уже
известным категориям недетерминизма (имя автора, капитализация серии,
перестановка дробных номеров), теперь зафиксированы в одно конкретное
значение; данных не потеряно.

Трассировкой (временные debug-print в `series_processor.py`,
`pass4_consensus.py`, `pass2_series_filename.py`) установлено: ни
`apply_series_consensus()`, ни его дублирующая логика в
`pass4_consensus.py` (~1093-1096, тоже пропатчена в этой сессии для

источник — ТРЕТИЙ, независимый механизм: блок **"SERIES SUFFIX
CORRECTION"** в `Pass4Consensus.execute()` (`pass4_consensus.py`,
~строка 1144), который существует для другого легитимного случая
("Я - Миха 1." → "Миха" ⊂ "Я - Миха", восстановить обрезанный префикс).

Причина: на момент, когда этот блок строит `full_series` (все
`proposed_series` с "надёжным" источником по автору), `proposed_series`
folder_dataset-записи из вложенной "Автор\Серия" структуры
(`...\Поселягин-Владимир\Криминал\1. Дон.fb2`) **ещё содержит сырой**
`"Поселягин-Владимир\Криминал"` — POST-CHECK в `regen_csv.py`
(строка ~1159), который его отрезает, выполняется ПОЗЖЕ, уже ПОСЛЕ
Pass 4. SUFFIX CORRECTION видит короткое чистое "Криминал" (у соседнего
filename-файла) как суффикс длинного грязного варианта и "исправляет"
чистую запись до грязной — ровно наоборот тому, что должно произойти.

Фикс: в построении `full_series` исключаем любые значения с `\` —
дешёвая, безопасная защита независимо от того, ПОЧЕМУ у upstream-записи
временно грязное значение.

Закреплено тестом на точном срезе реальных данных (не синтетика "из
головы", а буквально записанное состояние двух реальных записей на
момент входа в `Pass4Consensus.execute()`):
`tests/integration/fb2parser_core/test_author_series_consensus.py::
TestSeriesSuffixCorrectionFolderPathLeak`. Полный regression-набор

  многосоставными инициалами автора в имени).

## Баг №11 — самоподтверждающаяся metadata_series ложно сливала несвязанные серии в `find_groups()` — ✅ Починено

Найден пользователем через реальную группу "Лисина Александра": серия
"Времена" (10 книг, полностью независимая) исчезала из списка — вместо
неё показывалась "Тёмные времена" из 10 книг, хотя реальная "Тёмные
времена" содержит всего 3 книги ("01 Враг.fb2", "02 Попутчик.fb2", "03
Хозяин.fb2"). При синхронизации с `delete_sources=True` эти 3 реальные
книги были бы удалены как "дубликаты".

Причина — в комбинированном слиянии бакетов `find_groups()`: короткая
серия "времена" текстово является хвостовым суффиксом длинной серии
"темные времена" (`_word_suffix_key`), и по правилам слияния требуется
metadata-подтверждение — хотя бы одна запись из бакета ДЛИННОЙ серии
должна иметь `metadata_series`, совпадающий с короткой. Но проверка не
исключала тривиальный случай: одна из книг папки «Тёмные времена» имела
`metadata_series="Темные времена"` — то есть ПОЛНОСТЬЮ совпадающий с
именем ЕЁ ЖЕ собственного (длинного) бакета, а не с короткой серией.
Поскольку "времена" — последнее слово в "темные времена",
`_word_suffix_key("времена", "темные времена")` возвращал True, и такое
самоподтверждение (metadata == собственный длинный бакет) ошибочно
принималось как доказательство связи с СОВСЕМ другой короткой серией.

Фикс: исключаем из подтверждения `metadata_series`, полностью
совпадающий с каноническим (длинным) ключом бакета — такое значение
подтверждает только "эта книга принадлежит своей же папке", а не связь
с другой, более короткой серией.

Проверено на полной библиотеке Test1 (1676 групп, изолированно от
несвязанных правок `app_settings.json`/`genres.xml` через `git stash
push` на конкретный файл): ровно 1 отличие от baseline — "Времена"
(10 книг) и "Тёмные времена" (3 книги) корректно разделились на две
группы вместо одной ложно склеенной "Тёмные времена" (10 книг,
содержащей чужие файлы). Полный regression-suite (20→21 тест) не
затронут. Закреплено тестом:
`tests/integration/fb2parser_core/test_bucket_merge_self_referential_metadata.py`.

## Баг №12 — sync-time дедупликация фрагментировала компиляции и теряла числовой диапазон из имени файла — ✅ Починено

Найден пользователем через реальную группу "Лисина Александра / Артур
Рэйш": пре-компиляция (превью, `find_groups`/`compile_group`) верно
показывала "Ноналогия" (9 томов), но после реальной синхронизации
итоговый скомпилированный файл получал "Октология" (8) — числа не
совпадали.

Причина — совсем другой, более ранний и наивный шаг обработки:
`SynchronizationService._deduplicate_by_compilation()` +
`_build_target_filename()` (`synchronization.py`), который работает ДО
реального движка компиляции (`find_groups`/`compile_group`/`_run_stats`
в `fb2_compiler.py`) и понятия не имеет о полной картине серии. На
реальных файлах Рэйша (диапазоны 1-2, 3-4, 5-6, 7-8 + уже готовый
"Артур Рэйш (Сборник, кн. 1-4)", покрывающий 1-4) этот шаг:

1. Удалял только ОДИНОЧНЫЕ тома, полностью покрытые компиляцией — но
   НЕ удалял избыточные compilation-файлы друг относительно друга.
   Из-за этого "1-2" и "3-4" переезжали в библиотеку КАК ОТДЕЛЬНЫЕ
   файлы РЯДОМ с уже готовым "1-4" — контент томов 1-4 физически
   дублировался (существовал дважды).
2. Каждый выживший compilation-файл переименовывался НЕЗАВИСИМО, суффиксом
   посчитанным только по ЕГО СОБСТВЕННОМУ локальному диапазону
   (`_series_suffix(len(covered_volumes), lo, hi)` без знания об остальных
   диапазонах серии) — "1-2"→"Дилогия", "3-4"→"т. 3-4" и т.п. — вместо
   одной книги получался набор внутренне противоречивых файлов. Хуже:
   такое переименование НЕОБРАТИМО стирало из имени файла числовой
   диапазон (в "Дилогия" числа уже нет) — из-за чего последующий
   auto-compile, сканируя эти уже переименованные файлы в библиотеке, не
   мог восстановить их истинные позиции и в итоге считал диапазон серии
   неверно ("Октология" вместо "Ноналогия").

Фикс (в два этапа, второй — сужение первого после находки риска):

1. `_deduplicate_by_compilation()`: жадно (от большего диапазона к
   меньшему) дедуплицирует compilation-записи такой же связки
   (автор, серия) друг относительно друга — не только одиночки против
   компиляций. `_build_target_filename()` для compilation-записей больше
   не строит суффикс по локальному диапазону — сохраняет ОРИГИНАЛЬНОЕ имя
   файла (числовой диапазон остаётся читаемым для последующего
   auto-compile; финальный суффикс серии строит именно он, у него есть
   полная картина).
2. Первая версия фикса на полной библиотеке Test1 дала слишком широкий
   эффект — 120 новых удалений вместо ожидаемых 2-4 для целевого случая.
   Разбор показал реальный риск: часть "покрытий" определялась не по
   явному числу, а по УГАДАННОМУ ключевому слову (`_COMPILATION_KEYWORDS`,
   напр. "трилогия"→{1,2,3}) — у серии "Волжане"
   (Архипов Андрей) нашлось 3 РАЗНЫХ физических файла ("Поветлужье
   (трилогия)", "Волжане (Волжане. Трилогия)", "Цикл «Волжане»"), все
   классифицируются как покрывающие {1,2,3} — но совпадение УГАДАННОГО
   диапазона не доказывает идентичность контента (в отличие от явного
   числового диапазона, как у Рэйша). `_classify_record()` теперь
   возвращает флаг `confident` (True только для явного числа —
   `series_number`-диапазон, "(N-M)" в имени/заголовке, "Том N"; False —
   для угаданного по слову). Новая жадная дедупликация участвует ТОЛЬКО
   между confident-компиляциями; неуверенные ("трилогия" и т.п.) никогда
   не удаляются и никогда не служат основанием для удаления других — та
   же философия "безопаснее ничего не делать", что уже была у веток
   одиночных томов в этой функции.

Проверено на полной библиотеке Test1 (изолированно от несвязанных правок
через `git stash push` на конкретный файл): после сужения diff от
baseline составил 75 новых удалений (было 120 до сужения) — все
проверенные образцы оказались настоящими дубликатами с явным числовым
диапазоном (напр. "Оружейники 1-3"/"4-6" существуют БУКВАЛЬНО в двух
разных папках библиотеки как точные копии; "Ван Ван из Чайны 1-4"
полностью покрыт более полным переизданием "1-5"), рискованные
guessed-диапазон случаи ("Волжане" и подобные) из diff'а пропали. Полный
regression-suite (21→24 теста) не затронут. Закреплено тестами:
`tests/integration/fb2parser_core/test_sync_compilation_dedup.py`.

## Баг №13 — однословная серия перед "Книги N-M" терялась, а затем ложно переклеивалась на чужую серию по совпадению последнего слова — ✅ Починено

после фикса бага №11 логика компиляции всё ещё не видела, что уже

## Баг №14 — единственный выживший после дедупликации compilation-файл никогда не переименовывался — ✅ Починено

Найден пользователем при живой проверке реальной синхронизации (после
фиксов багов №12/№13): в библиотеке файл серии "Времена" остался под
СЫРЫМ исходным именем "Времена. Книги 1-10.fb2" — без автора и суффикса
серии — хотя ВСЕ остальные серии автора получили правильное имя вида
"Лисина Александра - Название (Суффикс).fb2".

Причина: дедупликация в баге №12 теперь ПРАВИЛЬНО удаляет все 10
одиночных томов "Времена" как покрытые уже готовым файлом "Времена.
Книги 1-10.fb2" — но в результате этот файл остаётся ЕДИНСТВЕННЫМ
выжившим для своей (автор, серия) связки. `_build_target_filename()`
(баг №12) намеренно сохраняет для compilation-записей ОРИГИНАЛЬНОЕ имя
файла, откладывая построение финального суффикса на более поздний шаг —
`auto_compile_library()` через `find_groups()`, у которого есть полная
картина всех томов серии. Но `find_groups()` требует МИНИМУМ 2 файла,
чтобы вообще считать это "группой" (`if len(recs) < 2: continue`) — если
дедупликация схлопнула серию до 1 файла, эта группа никогда не создаётся
и никогда не переименовывается.

Фикс: сразу после дедупликации в `synchronize()` вычисляем, для каких
(автор, серия) связок остался РОВНО один compilation-файл с известным
диапазоном, начинающимся с 1 (`_sole_full_compilation_paths`) — для них
`_build_target_filename()` строит финальное имя ("Автор - Серия
(Суффикс).fb2") сразу, а не откладывает на auto-compile: раз файл один
и покрывает диапазон с первого тома, это уже вся серия целиком, полная
картина уже известна на этом шаге.

Проверено синтетическим воспроизведением реального случая (10 одиночных
томов + готовый файл "1-10", дедупликация оставляет 1 файл → получает
имя "Лисина Александра - Времена (Декалогия).fb2"). Полный
regression-suite (28→29 тестов) не затронут. Закреплено тестом:
`tests/integration/fb2parser_core/test_sync_compilation_dedup.py`
(`TestSoleSurvivingCompilationGetsProperName`).

## Баг №15 — папка автора с фамилией в скобках посередине протекала в proposed_series — ✅ Починено

поэтому обрезка не срабатывала, сравнение "дедушка == автор" не

принималась за "серию верхнего уровня".

Фикс: сравнение дополнено ещё одной нормализованной версией имени папки
— с скобками, вырезанными ОТОВСЮДУ в строке, а не только с конца.

протёкшего пути. Побочных эффектов на остальной библиотеке нет. Полный

## Баг №16 — слияние ≥2 "сырых" дуг с разрывом в нумерации теряло номера дуг в суффиксе — ✅ Починено

Найден пользователем через сравнение двух реальных compile-превью в веб-UI

Проверено на полной библиотеке Test1 (1656 групп, изолированно от
несвязанных правок): 3 отличия от baseline — целевой случай (Иванович

(5+6 книг) — новый суффикс лишь честно показал уже существующий разлом

самого разлома НЕ разобрана — отдельная задача на будущее (возможно,

## Баг №17 — "разлом" серии "Пространство" объяснён: слитные инициалы в `<middle-name>` не распознавались наравне с обычным написанием — ✅ Починено

Продолжение расследования бага №16: разбирая, почему "Абрахам Дэниел
(Кори Джеймс), Тай Френк / Пространство" (The Expanse) распадалась на 2
группы вместо одной при полном скане библиотеки (при скане только своей
папки — 1 группа, 13 книг, `series_complete=True`), нашли точную причину
через потомную трассировку (`_chk2`-чекпойнты после каждого PASS в
`regen_csv.regenerate()`):

```
Исходные <middle-name> в FB2:
  большинство книг: "" или "С. А."   (пусто или с пробелом)
  книги 5 и 6:       "С.А."           (инициалы слитно, без пробела)

PASS 2 (метаданные):        'Джеймс Кори'    | 'Джеймс С.А. Кори'   — как есть
PASS 3 (нормализация):      'Джеймс Кори'    | 'С.А. Джеймс Кори'   — только у 5/6 переставило инициалы вперёд
PASS 4 (консенсус серии):   'С. Кори Джеймс' | 'С.А. Джеймс Кори'   — консенсус тронул книгу 1, книги 5/6 пропустил
PASS 5 (author_surname_conversions): 'С. Абрахам Дэниел (Кори Джеймс)' | 'С.А. Джеймс Кори' — конверсия сработала для книги 1, для 5/6 — нет
```

Слитная запись "С.А." (без пробела) выглядит как ОДИН непрерывный токен —
ни перестановка порядка слов (Pass 3), ни консенсус по серии (Pass 4), ни
`author_surname_conversions` (Pass 5) не распознают её так же, как
обычное написание ("С. А." с пробелом, или полное отсутствие инициалов) —
книги 5 и 6 проходят все три прохода нетронутыми, получая другого
финального автора, чем 11 остальных книг той же серии.

Фикс: вставляем пробел между слитными инициалами ("С.А." → "С. А.") сразу
на этапе извлечения метаданных, в `fb2_sax_extractor.py` — единственный
источник правды для всех дальнейших проходов.

**Первая версия фикса была слишком широкой** и сама внесла регрессию —
поймано полным библиотечным diff'ом ПЕРЕД коммитом: регэксп применялся ко
ВСЕЙ объединённой строке имени автора, из-за чего цепляло и
самостоятельные псевдонимы-инициалы БЕЗ фамилии вовсе — реальный случай
"N.B. ОЯШ 1-2.fb2" (`<first-name>N.B.</first-name>`, `<last-name>` пустой)
превращался в "N. B.", а затем downstream-перестановка порядка слов
портила его в "B. N." — совершенно другое, испорченное "имя". Сузили
область действия: регэксп применяется ТОЛЬКО к полю `middle_name` ДО его
объединения с first/last — для одиночного психевдонима-без-фамилии
middle_name всегда пуст, значит фикс его не касается.

Проверено на полной библиотеке Test1 (12117 записей, изолированно от
несвязанных правок): после сужения — ровно 2 отличия от baseline (книги 5

побочных изменения ("N.B." → "B. N."; "Майерс Б.Р." → переставлено,
частично нейтрально/полезно, но непроверено намеренно — решили не тащить
незапланированное изменение) — оба пропали после сужения. `find_groups()`
теперь корректно собирает всю серию "Пространство" в одну 13-книжную
группу. Полный regression-suite (44→49/51 тестов) не затронут. Закреплено
тестами: `tests/unit/fb2parser_core/test_sax_extractor_initials.py`
(включая `TestStandaloneInitialsPseudonymUntouched` — специально на
случай "N.B.", чтобы не повторить сужение задним числом).

## Баг №18 — компиляция подставляла genre="other" вместо жанра библиотечной папки — ✅ Починено

Найден пользователем визуально — на графике распределения жанров в
SOPDS-каталоге обнаружилась категория "other" (34 книги), хотя такой
жанровой папки в физической библиотеке нет вовсе (только "Фантастика" и
"Политический боевик"). Все 34 книги оказались скомпилированными файлами
("Дилогия", "в N книгах" и т.п.).

Причина — `compile_group()` (fb2_compiler.py) брал жанр итогового файла
ТОЛЬКО из `<genre>` метаданных ПЕРВОЙ исходной книги группы
(`meta = self._extract_metadata(group.books[0])`); при пустом теге —
жёстко подставлял заглушку `<genre>other</genre>`. У файлов-кандидатов на
компиляцию (обычно наспех докачанные скрейпленные тома) этот тег в
метаданных часто пуст — при этом сама библиотека уже организована по
жанровым папкам (пользователь синхронизирует ФАЙЛ в папку жанра только
ОДИН раз, всем файлам этой папки присваивается один и тот же жанр), т.е.
правильный жанр компиляции всегда уже известен из расположения файла и
не нуждается в повторном угадывании по метаданным.

Фикс: `compile_group()` получил необязательный параметр `genre_override`
— если задан, используется вместо чтения `<genre>` из первой книги.
`auto_compile_library()` (единственный реальный вызывающий код которой —
`fb2parser_web.views._run_compile_pass`, всегда получающая настоящий,
организованный по жанрам `library_path`) вычисляет его как первый
сегмент пути группы относительно `library_path` и передаёт в
`compile_group()`.

**Ручная чистка уже возникших 34 записей** (без изменения кода —
перепривязка к правильному жанру задним числом, отдельно от этого
фикса): переписан `<genre>other</genre>` → `<genre>Фантастика</genre>` в
самих FB2-файлах (round-trip через `fb2_utils.read_fb2_bytes`/
`write_fb2_bytes`, включая один `.fb2.zip`), плюс прямая правка
БД-каталога (SOPDS не перечитывает метаданные уже известных ему книг при
повторном скане — `sopdscan.processfile()` пропускает существующие
записи целиком, поэтому только правки файла недостаточно): все 34
`Book`-записи перепривязаны с жанра `other` на `фантастика`, пустой узел
`Genre(subsection='other')` удалён.

**Продолжение (найдено пользователем сразу после этого фикса — ещё 3 файла
с genre="other"):** `genre_override`, переданный из `auto_compile_library()`,
закрывает только ОДИН из двух реальных путей компиляции. Второй —
ручной инструмент "Normalize → Compiler" (`compiler_run()` в
`fb2parser_web/views.py`) — зовёт `compile_group()` напрямую, вообще без
`genre_override`. Реальный случай: 3 файла ("Квантовые джунгли", "Игра
не для всех", "Зург") получили `genre="other"`, хотя лежали внутри
"Фантастика" — они были скомпилированы через ЭТОТ путь.

Фикс расширен: `compile_group()` теперь сам определяет жанр через новый
внутренний метод `_resolve_compile_genre()` с приоритетом
`genre_override` → `<genre>` метаданных первой книги → совпадение
сегмента пути первой книги с именем узла в `genres.xml` (safety-net для
вызывающего кода, не передающего `genre_override` явно) → `"other"` как
крайний случай. Заодно найден и попутно исправлен пре-существующий баг
в `SettingsManager.get_genres_file_path()`: функция безусловно
возвращала сохранённый путь к `genres.xml`, даже если он на самом деле
не существует (напр. дефолтное относительное `"genres.xml"`,
не резолвящееся в текущий рабочий каталог процесса) — `_resolve_compile_genre()`

иначе использует тот же дефолт, что `fb2parser_bridge._genres_path()`.

## Баг №19 — двусоставный псевдоним автора матчился как «Серия» в имени файла — ✅ Починено

Найден пользователем визуально в сгенерированном `regen_Test1.csv`:
"Битон М. С. - Хэмиш Макбет 1. Смерть сплетницы.fb2" (Marion Chesney,
пишет под псевдонимом "M.C. Beaton" / "Битон М. С.") получал
`proposed_series = "С.\Хэмиш Макбет"` вместо чистого "Хэмиш Макбет".

Причина найдена через потрочную трассировку (`sys.settrace`) —
статическое чтение гигантской `_extract_series_from_filename()` не
давало однозначного ответа, какая именно из десятков веток сработала.
`BlockLevelPatternMatcher` сматчил имя файла по паттерну "Author. Series.
SubSeries. Title" (score 0.977), разбив двусоставный псевдоним "М. С."
на Author="Битон М." + Series="С." — второй инициал автора ошибочно
принят за отдельный блок "Серия".

Фикс: после вызова `BlockLevelPatternMatcher`, если корень
`series_from_block` (до `\`, если есть) — голая инициаль
(`^[А-ЯЁA-Z]\.$`), результат отбрасывается. Но если сделать это
безусловно и просто дать функции искать дальше — БЕЗ metadata_series
более поздние, менее надёжные правила (Rule 3B) сами способны угадать
ДРУГОЙ ложный кандидат: поймано полным библиотечным diff'ом ДО коммита
— "Хьюитт Дж. М. - Идеальная деревня.fb2" (2 самостоятельные книги без
единой серии, metadata_series пуста) после отбрасывания "М." получал
"Хьюитт Дж" — тоже фрагмент имени автора, просто не пойманный отдельной
проверкой `_is_author_surname()` (та разбирает только ОДНО слово автора
целиком, не составные двусловные фрагменты). Итоговое правило:
отбрасывать безусловно, только если есть metadata_series (тогда дальше
по цепочке есть на что опереться для правильного результата — как для
"Хэмиш Макбет" и ещё двух реальных случаев ниже); без metadata_series —
сразу возвращать "серии нет" (`None`), не продолжая угадывать.

Проверено на полной библиотеке Test1 (11279 записей, изолированно от
несвязанных правок): 3 отличия от baseline — все настоящие исправления
того же класса бага (двусоставные инициалы автора, ошибочно принятые за
серию): "Хэмиш Макбет" (2 файла, целевой случай), "Соловьев С. Ю. -
Русскiй детектiвъ" (4 файла, было `"Ю.\Русскiй детектiвъ"`), "Шуинар
М. М. - Детектив Джо Фурнье" (1 файл, было просто `"М."`). "Хьюитт Дж.
М." — единственный найденный при первой (слишком широкой) версии фикса
побочный эффект — из итогового diff'а пропал полностью после сужения.
Полный regression-suite (54→58 тестов) не затронут. Закреплено тестами:
`tests/integration/fb2parser_core/test_block_matcher_initial_as_series.py`
(4 теста, включая `test_two_standalone_books_no_metadata_get_no_series`
— специально на случай "Хьюитт", чтобы не повторить сужение задним
числом).

## Баг №20 — синхронизация не учитывала, что библиотечный файл может быть СЖАТ (`.fb2.zip`) — ✅ Починено (часть 1 из 3)

Пользователь попросил проверить, умеет ли синхронизация корректно
работать со смешанными данными: библиотека частично сжата функцией
"Сжать" (Library → Compress), источники при синхронизации всегда
приходят несжатыми `.fb2`. Проверка по всем аспектам (поиск дубликатов,
сборка/дополнение компиляций, коллизии имён) выявила 2 реальных бага в
одном и том же месте — `synchronize()`'s проверке коллизии итогового
имени (см. баг про "Васильев Андрей / Ученики Ворона" выше).

**1. Коллизия с уже сжатым файлом не обнаруживалась вовсе.** Итоговое
имя компиляции строится детерминированно и всегда с расширением `.fb2`
(`target_file = target_dir / target_name`). Если библиотека уже
содержит файл этой же серии в виде `<target_name>.fb2.zip`,
`target_file.exists()` возвращает `False` — коллизия просто не
замечалась, и источник молча ложился в библиотеку РЯДОМ как отдельный,
никем не распознанный дубликат контента.

**2. Сравнение размеров при коллизии сравнивало байты на диске, а не
реальное содержимое.** `_resolve_target_collision()` сравнивал
`source_file.stat().st_size` с `target_file.stat().st_size` напрямую.
Сжатый `.zip` на диске почти всегда МЕНЬШЕ несжатого `.fb2` с тем же (или
даже большим) реальным содержимым — источник ложно считался бы "полнее"
существующего сжатого файла и заменял бы его избыточным несжатым дублем:
риск потери правильного, уже сжатого файла библиотеки.

Фикс: проверка коллизии теперь ищет ОБА варианта имени (`target_name` и
`target_name + '.zip'`); `_resolve_target_collision()` сравнивает длину
РАСПАКОВАННОГО содержимого через `read_fb2_bytes()` (уже прозрачно
читает оба формата), а не байты на диске.

Проверено юнит-тестами (`_resolve_target_collision()` напрямую, с
реальным `.fb2.zip`-фикстурой через `zipfile`): содержимое одинаковое,
но сжатый target меньше на диске — источник корректно распознаётся как
избыточный дубль, а не заменяет существующий файл; источник
ДЕЙСТВИТЕЛЬНО больше по содержимому — по-прежнему корректно заменяет
сжатый target. Полный regression-suite (58→66 тестов, считая слитые с
другой машины) не затронут. Закреплено тестами:
`tests/integration/fb2parser_core/test_sync_compilation_dedup.py`
(`TestResolveTargetCollisionWithCompressedLibraryTarget`).

## Баг №20, часть 2 — компиляция всегда писала несжатый результат, даже дополняя сжатую серию — ✅ Починено

Продолжение проверки мешаных данных (часть 1 — выше). `compile_group()`
в `fb2_compiler.py` всегда сохранял итоговый файл через
`output_path.write_text(..., encoding='utf-8')` — то есть ПЛОСКИМ `.fb2`,
даже если группа дополняет ранее сжатую (через "Сжать" в Library) серию:
один из исходников группы — это уже существующий `.fb2.zip`, который
дополняется новым томом. Результат молча "расжимал" бы такую серию
обратно в `.fb2`, рассинхронизируя её формат с остальной библиотекой —
пользователю пришлось бы вручную пересжимать файл заново после каждого
дополнения тома.

Тот же баг был и во втором месте — в `cleanup_only`-ветке (переименование
без новой компиляции, когда обновляется только имя файла по схеме
"Автор - Серия (Суффикс)"): новое имя всегда строилось с расширением
`.fb2`, независимо от реального формата старого файла — `.fb2.zip` при
переименовании превратился бы в файл с именем `....fb2`, физически
оставаясь ZIP-архивом (несовпадение имени и формата).

Фикс: перед записью проверяется, есть ли среди исходников группы файл с
именем `*.fb2.zip` — если да, итоговое имя получает суффикс `.zip`, а
запись идёт через `fb2_utils.write_fb2_bytes()` (сохраняет формат по
имени файла). В `cleanup_only`-ветке новое имя при переименовании
аналогично наследует `.zip`, если исходный файл был сжат.

Проверено юнит-тестами: полный пайплайн (`generate_csv` →
`find_groups()` → `compile_group()`) на реальной группе из двух томов,
один из которых предварительно сжат через `compress_fb2_file()`, —
результат действительно `.fb2.zip` с корректным читаемым (через
`read_fb2_bytes()`) содержимым обоих томов; отдельный тест подтверждает,
что без сжатых исходников результат по-прежнему остаётся плоским `.fb2`.
Тест `test_output_compressed_when_a_source_is_compressed` подтверждённо
падает без фикса (`git stash push -- src/fb2parser_core/fb2_compiler.py`)
и проходит с ним. Полный regression-suite (66→67 тестов, 1 xfail) не
затронут. Закреплено тестами:
`tests/unit/fb2parser_core/test_compile_output_preserves_compression.py`.

## Баг №20, часть 3 — выбор "лучшей" предкомпиляции и парная дедупликация тоже сравнивали байты на диске — ✅ Починено

Продолжение проверки смешанных данных (части 1-2 — выше). В
`fb2_compiler.py` нашлось ещё 2 места с той же слепотой к `.fb2.zip`:

1. **Выбор "лучшей" предкомпиляции при неточной защите от урезанных

Других мест со сравнением сырых байт на диске в синхронизации/компиляции

## Баг №21 — синхронизация падала на длинных именах файлов (Windows MAX_PATH) — ✅ Починено

Реальный случай: Микишин Фёдор / "Хан Батый и десантники" — название
книги с длинным подзаголовком-посвящением ("Книга 1. Выживание.
Альтернативная история с попаданцами. Посвящается курсантам военных
училищ СССР") давало итоговый путь синхронизации ровно в 260 символов.
`shutil.move()` в `_move_files()` падал с `[WinError 3] Системе не
удается найти указанный путь`, хотя обе папки (источник и назначение)
физически существовали — классическое поведение Windows API на пути,
превышающем MAX_PATH, при выключенной поддержке длинных путей.
Ошибка просто считалась как `errors += 1`, файл оставался
несинхронизированным без объяснения причины пользователю.

Причина: `_build_target_filename()` строит имя файла из автора + серии +
ПОЛНОГО названия книги (включая любые подзаголовки) без ограничения
длины — обычно этого достаточно, но у книг с длинными
посвящениями/подзаголовками итоговое имя может стать очень длинным, а
итоговый путь — превысить лимит ОС.

Фикс: добавлен `_shorten_filename_for_path_limit()` — вызывается сразу
после `_build_target_filename()` в `_move_files()`, перед вычислением
`target_file`. Если итоговый путь `target_dir/target_name` превышает
`_MAX_PATH = 259`, обрезает "хвост" ИМЕНИ ФАЙЛА (не трогая путь к
папке — она определяется жанром/автором/серией) до умещающейся длины,
сохраняя расширение `.fb2` и добавляя маркер обрезки `…`. Каталог
(глубина жанр/автор/серия) не корректируется — предполагается, что
пользователь либо не создаёт аномально глубокую иерархию, либо включит
поддержку длинных путей Windows отдельно; здесь чинится конкретно
падение на длинном ИМЕНИ ФАЙЛА, что покрывает реальный случай.

Рассматривались два подхода: (1) обрезка по числу символов "в лоб" —
может оборвать текст прямо посреди слова или номера тома; (2)
семантическая эвристика "отбросить всё после второго предложения" (тогда
"Книга 1. Выживание. Альтернативная история с попаданцами..." → "Книга
1. Выживание.") — даёт красивый результат для этого конкретного случая,
но ненадёжна как общее правило (не факт, что "лишний хвост" всегда идёт
третьим предложением у ДРУГИХ книг — может отрезать значимую часть
настоящего названия). Выбран подход (1) как единственный универсально
безопасный, применяемый ТОЛЬКО когда путь реально не помещается (для
подавляющего большинства файлов ничего не меняется).

Проверено юнит-тестами: короткое имя не трогается; длинное имя (тот же
образующий путь длиной 260 символов, что и в реальном случае) обрезается
до факта ≤259 символов итогового пути, сохраняя расширение и добавляя
"…". Полный regression-suite (68→71 тестов, 1 xfail) не затронут.
Закреплено тестами:
`tests/unit/fb2parser_core/test_sync_max_path_truncation.py`.

## Баг №22 — слияние сырых дуг без разрыва в нумерации всегда давало голое "в N книгах" — ✅ Починено

Реальный случай (замечен пользователем): Бэккер Ричард / "Второй
Апокалипсис" — 2 подсерии-дуги ("Второй Апокалипсис 1 \ Князь пустоты" —
3 сырых книги, "Второй Апокалипсис 2 \ Аспект-Император" — 4 сырых
книги), обе завершены, разрыва в нумерации дуг нет. `compute_group_suffix()`
давал голое "в 7 книгах" вместо более информативного "Дилогия в 7
книгах" — хотя само название подсерий ("Второй Апокалипсис 1"/"Второй
Апокалипсис 2") однозначно называет число дуг.

Причина: ветка слияния "сырых" (не предкомпилированных) дуг — в отличие
от ветки для уже готовых предкомпилированных дуг (см. "Мир вечного",
баг №19) — по прежней (сознательной) договорённости ВСЕГДА выдавала
голое "в N книгах", без словесной формы ("Дилогия"/"Трилогия"),
независимо от того, завершена серия или нет. Исключение вводилось ради
другого реального случая — "Иванович Юрий / Миры Доставки" (см. баг,
зафиксированный в `test_compute_group_suffix_arc_gap.py`): там дуги 1-3
сливаются, а дуга 4 отсутствует (разрыв в нумерации) — словесная форма
там действительно замаскировала бы, какие именно дуги внутри файла.
Но для ПОЛНОСТЬЮ завершённой серии без разрыва (случай Бэккера) эта
маскировка не актуальна — число дуг читается напрямую из структуры
серии.

Фикс: в `compute_group_suffix()` (`fb2_compiler.py`) ветка слияния сырых
дуг при `_sc_compile=True` (нет разрыва, нет исключений) теперь вызывает
тот же `_series_suffix()`, что и ветка предкомпилированных дуг, получая
словесную форму. Ветка с разрывом в нумерации (`_sc_compile=False`)
не тронута — там по-прежнему явный диапазон дуг ("ч. 1-3 в 9 книгах"),
как и раньше.

Проверено интеграционными тестами: новый тест на реальной структуре
Бэккера (2 полных дуги → "Дилогия в 7 книгах"), подтверждённо падающий
без фикса (`git stash push -- src/fb2parser_core/fb2_compiler.py`) —
раньше получалось голое "в 7 книгах". Существующий тест
`test_compute_group_suffix_arc_gap.py::test_merged_complete_arcs_stay_plain`
(закреплял именно старое поведение "в 9 книгах" для завершённой серии)
обновлён на новое ожидание "Трилогия в 9 книгах" — старое имя теста и
докстринг переименованы, чтобы отражать текущий, а не прошлый дизайн;
тест на РАЗРЫВ в нумерации (`test_merged_incomplete_arcs_show_range`,
"ч. 1-3 в 9 книгах") не менялся и по-прежнему проходит без изменений.
Полный regression-suite (71→72 тестов, 1 xfail) не затронут. Закреплено
тестами:
`tests/integration/fb2parser_core/test_compute_group_suffix_complete_raw_arcs.py`,
`tests/integration/fb2parser_core/test_compute_group_suffix_arc_gap.py`.

## Баг №23 — точных совпадений по БД найдено больше, чем показано удалённых — ✅ Починено

Реальный случай (замечен пользователем в отчёте синхронизации): «точных
совпадений (БД/имя файла): 13», но «всего удалено дублей: 3» — разница

Причина: ветка проверки точного совпадения (автор, серия, название) с
уже существующей записью БД (`_build_folder_structure()`,
`synchronization.py`) инкрементирует `duplicates_found` и РЕАЛЬНО удаляет
файл-дубликат с диска (`os.unlink()`), но никогда не увеличивала
`duplicates_deleted` — этот счётчик рос только в других местах
(`_resolve_target_collision`, `_delete_records_and_files`, дедупликация
компиляций), никак не связанных с этой конкретной проверкой. Файлы
реально удалялись, просто мимо счётчика — расхождение 13 vs 3 создавало
ложное впечатление, что что-то не досделано.

Фикс: добавлен инкремент `duplicates_deleted` сразу после успешного
`os.unlink()` в этой ветке — оба счётчика теперь синхронно отражают
реальное число удалений.

Проверено юнит-тестами: удаление реально существующего файла-дубликата
инкрементирует ОБА счётчика (`duplicates_found` и `duplicates_deleted`);
отдельный тест — если файл к моменту проверки уже отсутствует на диске
(напр. удалён более ранним прогоном), находка засчитывается, но
`duplicates_deleted` не растёт (нечего было удалять). Подтверждённо
падает без фикса (`git stash push -- src/fb2parser_core/synchronization.py`).
Полный regression-suite (72→74 тестов, 1 xfail) не затронут. Закреплено
тестами: `tests/unit/fb2parser_core/test_sync_db_duplicate_stats.py`.

## Баг №24 — псевдоним из author_surname_conversions не переставлялся в "Фамилия Имя" — ✅ Починено

Реальный случай (замечен пользователем в CSV): Александр Айзенберг,
пишущий под псевдонимом «Берг» (серия «Антиблицкриг»), — `app_settings.json`
уже содержит `"author_surname_conversions": {"Айзенберг": "Берг"}`.
`proposed_author` для всех книг серии оставался «Александр Берг» (Имя
Фамилия) вместо правильного «Берг Александр» (Фамилия Имя) — единственный
стандартный порядок, используемый везде в библиотеке.

Причина: `normalize_format()` в `Pass3Normalize.execute()` (`pass3_normalize.py`)
КОРРЕКТНО переставляет «Александр Берг» → «Берг Александр» — но
защитная эвристика (введена ради других реальных случаев, напр.
«Линдквист Йон Айвиде», где normalize_format иногда переставляет по
ложному срабатыванию) откатывает ЛЮБУЮ перестановку, если сырые слова
`metadata_authors` её не подтверждают. Метаданные FB2-файла хранят
настоящую фамилию автора («Александр Айзенберг»), а не псевдоним — сырое
слово «айзенберг» никогда не совпадает с «берг» напрямую, подтверждение
не проходит, реордер молча откатывается, оставляя неверный порядок слов
навсегда.

Фикс: при сборке множества "подтверждающих" слов метаданных (`_meta_ends`
в `pass3_normalize.py`) для каждого автора из `metadata_authors`
добавляются слова НЕ ТОЛЬКО как есть, но и ПОСЛЕ применения
`author_surname_conversions` (`AuthorNormalizer.apply_conversions()`) —
"Александр Айзенберг" → "Александр Берг", и слово "берг" теперь
корректно подтверждает перестановку.

Проверено юнит-тестами: `Pass3Normalize.execute()` на записи с
`author_source="folder_dataset"`, `proposed_author="Александр Берг"`,
`metadata_authors="Александр Айзенберг"` — результат "Берг Александр".
Отдельный sanity-тест подтверждает, что обычная (без псевдонима)
перестановка, где метаданные напрямую содержат нужную фамилию
("Александр Тамоников" + метаданные "Александр Александрович
Тамоников" → "Тамоников Александр"), по-прежнему работает без изменений.
Подтверждённо падает без фикса
(`git stash push -- src/fb2parser_core/passes/pass3_normalize.py`).
Полный regression-suite (74→76 тестов, 1 xfail) не затронут. Закреплено
тестами:
`tests/unit/fb2parser_core/test_pass3_pseudonym_conversion_reorder.py`.

## Баг №25 — декоративный контейнер-обёртка протекал в значение серии — ✅ Починено

Реальный случай (замечен пользователем в CSV): контейнер "Серия -
«Вселенная S-T-I-K-S»" содержит несколько ПЛОСКИХ подсерий-папок —
"1. Похождения Карата", "2. Приключения Элли", "3. Наемник Айвэн" и
т.д., а также "Дополнения" (без номера). Для файлов из "Дополнения"
`proposed_series` получался "Серия - «Вселенная
S-T-I-K-S»\Дополнения" — дедушкина папка-обёртка целиком подмешивалась в
серию.

Первая версия фикса ошибочно решила, что проблема — только в
НЕОБРЕЗАННОМ декоративном тексте "Серия - «" (который вообще-то обрезает
`_postcheck_series_folder_blacklist()`, но выполняется РАНЬШЕ, чем
`_postcheck_build_subfolder_hierarchy()`, добавляющий этот текст).
Пользователь указал сравнить с СОСЕДНИМИ значениями в том же CSV — и это
вскрыло настоящую причину: для пронумерованных подсерий ("1. Похождения
Карата" и т.п.) дедушка вообще НИКОГДА не подмешивается — guard
`parent_name_norm == ps_norm` не совпадает, т.к. имя папки содержит
номер ("1. похождения карата"), а `proposed_series` уже очищено от
номера ("похождения карата") другим постчеком. "Дополнения" (без
номера) совпадает буква-в-букву — единственная причина, по которой
дедушка вообще подмешивался ИМЕННО сюда, а не полноценная логика
"серия верхнего уровня". Сам дедушка — чисто декоративный
организационный контейнер (обёртка вида "Серия - «Название»"), а не
настоящая умбрелла-серия, и не должен подмешиваться НИКОГДА, независимо
от текста внутри него.

Правильный фикс: `_postcheck_build_subfolder_hierarchy()` (regen_csv.py)
пропускает дедушку ЦЕЛИКОМ (не только его текст), если имя дедушкиной
папки начинается с одного из `series_folder_prefixes_to_strip` —
такая папка заведомо декоративная обёртка, а не годная "серия верхнего
уровня" ни в каком виде.

Проверено интеграционным тестом (по образцу уже существующего
`TestSubfolderHierarchyAuthorFolderWithMidwordParens` из того же файла):
2 файла с той же структурой, что и реальный случай (S-T-I-K-S) — после
фикса `proposed_series` остаётся чистым "Дополнения", без всякого
подмешивания дедушки — как и у пронумерованных соседей. Подтверждённо
падает без фикса (`git stash push -- src/fb2parser_core/regen_csv.py`).
Полный regression-suite (76→77 тестов, 1 xfail) не затронут. Закреплено
тестом:
`tests/integration/fb2parser_core/test_author_series_consensus.py::TestSubfolderHierarchySkipsDecorativeContainerFolder`.

## Баг №26 — "безномерная" книга-arc-1 не присоединялась к уже подтверждённой серии — ✅ Починено

Реальный случай (замечен пользователем в CSV): "hawk1. Фарт.fb2" (arc 1,
БЕЗ номера в имени файла) оставался вообще без серии, хотя "hawk1. Фарт
2. По следам друзей..." (arc 2, тот же автор и папка) уже подтверждён как
часть серии "Фарт" через `filename_named_arc`
(`pass2_series_filename.py`). Файлы без номера в имени не совпадают ни с
одним существующим паттерном извлечения arc-номера — серия оставалась
пустой, разрывая связь между книгами одного цикла.

Фикс: новый постчек `_postcheck_link_base_arc_book_into_named_series()`
(regen_csv.py), запускается в конце цепочки постчеков (после
`_postcheck_strip_digit_prefix_author()`, до финального отката к
метаданным). Условия срабатывания намеренно узкие, чтобы не зацепить
чужие случаи:
  - `proposed_series` у записи пусто;
  - есть другая запись ТОГО ЖЕ автора и ТОЙ ЖЕ папки с
    `series_source == 'filename_named_arc'`, чей "корень" серии (первый
    сегмент до '\', без номера в конце — "Фарт 2" → "Фарт") совпадает по
    названию с `file_title` текущей записи;
  - номер "1" в этой серии/авторе/папке ещё никем не занят (иначе —
    конфликт нумерации, запись не трогаем).

При срабатывании: `proposed_series = root_base`, `series_number = "1"`,
`series_source = "filename_base_arc_consensus"` (отдельная метка, легко
отличимая от `filename_named_arc`).

Проверено интеграционными тестами: реальный случай (arc 1 без номера +
2 файла arc 2 с подтверждённым `filename_named_arc`) корректно
присоединяется; конфликт нумерации (номер "1" уже занят другой книгой) —
безномерная книга НЕ трогается; другой автор с тем же `file_title` —
НЕ совпадает (узость условия по автору+папке работает). Дополнительно
проверено на реальной библиотеке (`Test1`, папка `Фанфики`) — прогон
полного пайплайна корректно даёт `proposed_series="Фарт"`,
`series_number="1"` для `hawk1. Фарт.fb2`. Подтверждённо падает без
фикса (`git stash push -- src/fb2parser_core/regen_csv.py`). Полный
regression-suite (77→80 тестов, 1 xfail) не затронут. Закреплено
тестами:
`tests/integration/fb2parser_core/test_author_series_consensus.py::TestLinkBaseArcBookIntoNamedSeries`.
