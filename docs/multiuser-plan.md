# План реализации: многопользовательская библиотека

Проект и согласованные решения — `docs/multiuser-design.md`. Здесь — порядок
работ, шаги с файлами, тесты и границы коммитов. Этап 1 расписан подробно,
этапы 2–4 — укрупнённо (детализируются перед началом).

Каждый шаг — отдельный коммит после подтверждения пользователя; каждый шаг
оставляет проект рабочим, а поведение для пользователей — прежним, пока
вся библиотека принадлежит администратору и «открыта всем».

## 0. Соглашения (общие для всех шагов)

- **Один корень.** Владение хранится относительно `root_lib` (OPDS).
  У fb2parser свой `library_path` — сейчас ничто не требует их совпадения.
  Проверка `manage.py check` (Django system check) и предупреждение на
  странице настроек, если они различаются; операции fb2parser, пишущие в
  библиотеку, отказываются работать при расхождении (иначе владение
  разъедется с путями).
- **Канонический `rel_path`:** путь относительно `root_lib`, разделитель `/`,
  Unicode NFC, без `./`; для книги в zip — путь самого zip. Одна функция
  `ownership.rel_path(abs_path)` — других способов строить ключ нет.
  (Сейчас: `.library_cache.db` — то `\`, то `/`; `library_memory` — `/`;
  `Book.path` — родные разделители ОС.)
- **Файл без владельца принадлежит администратору** (первому активному
  суперпользователю; при нескольких — настройка). Это же правило — для
  ухода последнего владельца. Отсюда безопасный отказ: при любом сбое учёта
  книга становится «администраторской», а не видимой чужим.
- **Кто владелец при синхронизации:** пользователь, запустивший операцию
  (сейчас это всегда администратор); автосинхронизация и команды — администратор.
  В этапе 3 приёмник передаёт загрузившего.

### Шаг 1.2. Модуль учёта владения — ✅ сделано (2026-10-20)
Сделано: `opds_catalog/ownership.py` (`rel_path`, `book_rel_path`,
`assign`, `transfer`, `merge`, `release`, `owners`, `owner_set_key`,
`admin_user`), журнал `LibraryOwnershipLog` (миграция `0015`). Записи
каталога (`BookOwner`) по тому же пути обновляются сразу, не дожидаясь

`tests/integration/opds_catalog/test_ownership.py`. «Настройка при
нескольких суперпользователях» отложена: владелец по умолчанию — первый
активный суперпользователь.

Файл: `src/opds_catalog/ownership.py` (без Django-представлений; вызывается
и из fb2parser).

- `rel_path(abs_path) -> str` (соглашение 0), отказ для путей вне `root_lib`.
- `assign(rel_path, user, source, origin_name=..., origin_sha256=..., size=...)`.
- `transfer(old_rel, new_rel)` — переезд всех владельцев; если по новому
  пути уже есть владельцы — объединение.
- `merge(sources: list[rel], target_rel)` — объединение владельцев (для
  сборника), источники освобождаются.
- `release(rel_path, user=None)` — отзыв одного владельца или всех (файл
  удалён); при уходе последнего владельца у **существующего** файла —
  администратор.
- `owners(rel_path) -> set[User]`, `owner_set_key(rel_path)` — для группировки
  компилятора.
- Всё — в транзакции SQLite (`BEGIN IMMEDIATE`, как в баге про занятую базу
  — `test_sqlite_immediate_transactions`), с журналом изменений
  (`LibraryOwnershipLog`: кто, что, когда — пригодится и в этапе 4).

Тесты (unit): каждая функция; объединение; уход последнего → администратор;
путь вне корня → ошибка; разные разделители/NFC → один ключ.

### Шаг 1.3. Сканер и сверка — ✅ сделано (2026-10-20)
Сделано: владельцы новой записи каталога — в `opdsdb.addbook` (через неё
создаёт записи и сканер, и INPX) → `ownership.link_book`; сжатие —
`ownership.transfer` в `compress_catalogs`; сверка —
`ownership.reconcile` + команда `library_owners_check [--apply] [--force]`.
Уточнение по ходу: файл без владельца, автоматически отданный
администратору сканером или сверкой, помечается `source = auto` — сканер
может увидеть переехавший в обход учёта файл раньше сверки, и сверка должна
суметь вернуть его настоящему владельцу по отпечатку (осознанная передача
администратору при уходе последнего владельца — `source = admin`, её сверка
не трогает). Защита как у сканера: пропало больше 30 % (и больше 100)
файлов с владельцами — без `--force` ничего не снимается. Тесты:
`tests/integration/opds_catalog/test_ownership_scan_reconcile.py`.
На рабочих данных (отчёт): 6790 файлов, у всех есть владелец, расхождений 0.

Файлы: `src/opds_catalog/sopdscan.py`, `opdsdb.py`,
`src/fb2parser_web/compress_catalogs.py`, новая команда
`src/opds_catalog/management/commands/library_owners_check.py`.

- `addbook`/`refreshbook`: `BookOwner` по `LibraryFileOwner` для
  `rel_path` книги (`CAT_NORMAL`: `path/filename`; `CAT_ZIP`: `path`); нет
  владельцев → `assign(..., администратор)`.
- Логическое/физическое удаление `Book` — `BookOwner` не трогаем (каскад
  при физическом), `LibraryFileOwner` не трогаем: файл мог переехать, а
  перенос — забота операции, которая его двигала.
- `compress_catalogs.update(old, new)` — уже переносит `Book` на месте,
  добавить `ownership.transfer`.
- `library_owners_check [--apply]`:
  - файлы библиотеки без владельца → администратор;
  - владельцы путей, которых нет на диске → попытка найти файл по
    отпечатку текста `library_memory` (переживает перемещение, сжатие,
    правку тегов) и перенести; не нашли → журнал и удаление записи;
  - `BookOwner` ↔ `LibraryFileOwner` — пересборка расхождений;
  - отчёт без `--apply`.

Тесты: новая книга → владелец; книга в zip; сжатие сохраняет владельца;
сверка — сирота → администратор, переезд по отпечатку, отчёт без изменений.

### Шаг 1.4. Перенос владения в операциях fb2parser — ✅ сделано (2026-10-20)
Сделано: `fb2parser_core/ownership_hooks.py` — точка вызова без Django
(по умолчанию ничего не делает), реальный учёт подключает
`opds_catalog.apps.ready` (`ownership.LibraryOwnershipHooks`: абсолютные
пути → `rel_path`, пути вне библиотеки пропускаются, сбой учёта — в лог,
не прерывает операцию с файлами; расхождение чинит `library_owners_check`).
Вызовы: синхронизация (перенос, замена более полной версией — прежние
владельцы остаются, переезд со сжатого имени), переименование автора,
ручной перенос при сверке, удаление по списку, компилятор (сборник —
объединение владельцев исходников и дублей, `keep_sources` при
`delete_sources=False`; ветка «только очистка» — владельцы дублей
оставленному сборнику, переименование — перенос; `_delete_sources` —
снятие). Группировка: `find_groups` делит книги по набору владельцев и
ищет группы в каждой части отдельно (пока владелец у всех один — часть
одна, поведение прежнее; «золотой снимок» без изменений). Стоимость на
рабочей библиотеке: 0,56 мс на файл (6790 файлов — 3,8 с).
Упрощение этапа 1: владелец файлов, положенных синхронизацией, —
администратор (`admin_user()`), а не «запустивший»: запускать
синхронизацию сейчас может только персонал; пользователь-загрузивший
появится в этапе 3 (приёмник передаст его явно).
Тесты: `tests/integration/fb2parser_core/test_ownership_in_operations.py`
(9 тестов, fail-before 8/9; девятый — страховка «пути вне библиотеки не
трогаются»). Попутные дефекты из инвентаризации (блокировка `sync_lock`
для ручной компиляции, удаления по списку и ручного переноса; перезапись
`output_path` компилятором; неограниченное назначение жанра) — не в этом
шаге, отдельными коммитами.

Все операции, которые создают, перемещают или удаляют файлы внутри
библиотеки (инвентаризация 2026-10-19; операции над исходными папками,
временными файлами и кэшами владения не касаются):

| Операция | Где | Что делать |
|---|---|---|
| Синхронизация: перенос в библиотеку | `synchronization._move_files` (`shutil.move`), есть `moved_books` | `assign(new_rel, запустивший)` |
| Синхронизация: коллизия, входящий файл больше | `_resolve_target_collision` (удаляет файл библиотеки) | владельцы старого файла + запустивший (тот же путь — та же книга); если путь сменился `.fb2.zip` → `.fb2` — `transfer` |
| Ручной перенос при сверке | `views.sync_reconciliation_resolve` action `move` | `assign`; заодно запись в `.library_cache.db` (сейчас её нет) |
| Переименование автора | `rename_library_author` (уже `UPDATE books SET file_path`) | `transfer` на каждый файл |
| Сжатие | `compress_catalogs.update` | шаг 1.3 |
| Компиляция: переименование оставленного сборника | `fb2_compiler.compile_group` ветка `cleanup_only` (`old_path.rename`) | `transfer` |
| Компиляция: новый сборник | `compile_group` (запись `output_path`), `CompilationResult` | `merge(sources, output)` |
| Компиляция: удаление дублей/исходников | `_delete_sources` | `release(path)` (дубль с другими владельцами — сначала их на оставшийся файл, иначе потеря видимости) |
| Удаление по списку (мученики, битые, дубли) | `views._delete_paths_confined` | `release(path)` |
| Правка тегов, смена жанра на месте | `_patch_fb2_tags`, `genre_assign` | ничего (путь тот же) |

- **Компилятор группирует только книги с одинаковым набором владельцев**
  (`find_groups` / `_build_series_buckets`: ключ серии + `owner_set_key`).
  Пока всё у администратора — группы прежние (проверить «золотым снимком»).
- Попутные дефекты из инвентаризации (отдельными коммитами, до или в этом
  шаге): ручная компиляция, удаление по списку и ручной перенос при сверке —
  не под `sync_lock`; компилятор перезаписывает `output_path` без проверки
  существования (а если имя совпало с исходником — потом удаляет только что
  собранный файл); `assign_genre_multi`/`genre_scan_assign` не ограничены
  папкой.

Тесты: на каждую строку таблицы — владелец после операции; компиляция
книг разных владельцев — две группы; полный набор `tests/integration/fb2parser_core`
и «золотой снимок» без изменений.

## Этап 3. Приёмник загрузок (укрупнённо)
Перед началом — отдельный детальный проект (`docs/upload-pipeline.md`):
форма загрузки и входящая папка, проверки безопасности файлов, очередь
разбора, упрощённая проверка, дубли по `origin_sha256`, синхронизация с
владельцем, квоты, что из fb2parser доступно пользователю, а что — нет.

**Приоритет: низкий** — по словам владельца репозитория (2026-10-22),
функция пока не особо нужна; записано, чтобы не потерять решения.

### Согласованные решения (2026-10-22)
1. **Форматы — только FB2 и FB2.ZIP.** Разбор (6 проходов), синхронизация
   и компилятор работают только с FB2; EPUB проект умеет только читать
   (запись метаданных пришлось бы писать), MOBI/AZW3 — двоичные, правка —
   только через Calibre на сервере. Сайт и так отдаёт FB2 в EPUB/MOBI при
   скачивании.
2. **Загрузка** — в личную входящую папку `inbox/<id пользователя>/` вне
   библиотеки, без выбора папки. Проверки до разбора: размер файла и всей
   загрузки, формат, zip-бомбы, пути `../` в zip, безопасный разбор XML.
   Zip с папками распаковывается со структурой (разбор берёт автора и
   серию и из папок).
3. **Разбор** — фоновая задача, общая очередь, по одной за раз (два
   параллельных прогона уже давали `MemoryError` на Test2).
4. **Таблица для проверки**, все поля редактируются:
   Автор | Серия | № | Подсерия | № | Название | Жанр (+ исходное имя файла,
   только чтение). Номер в серии обязателен — без него серия ляжет без
   порядка.
   - **Жанр** — выпадающий список корневых жанров, не свободный текст: либо
     автоматически назначенный корневой жанр (как сейчас), либо — если
     ассоциация не сработала — код из файла, подсвеченный красным; такая
     книга блокирует синхронизацию, пока не выбран корневой жанр.
   - **Автор и серия** — подсказки из существующих, но только из видимых
     этому пользователю (иначе подсказки раскроют чужие библиотеки);
     проверка недопустимых для пути символов. Цель — опечатки не должны
     плодить новые папки авторов.
5. **«Синхронизировать» — только когда готова вся загрузка (вариант Б).**
   Кнопка неактивна, пока в таблице есть хоть одна неготовая книга
   (неопределённый жанр и т. п.); исправить или удалить её — и тогда
   уходит всё сразу. Причина: при частичной синхронизации (вариант А)
   оставшиеся книги могли бы так никогда и не попасть в библиотеку.
   Синхронизация — стандартная, владелец — загрузивший
   (`ownership_hooks.assign` для этого нужно научить принимать владельца),
   общая блокировка с задачами fb2parser суперпользователя, затем точечный
   скан, чтобы книги сразу появились в каталоге.
6. **Компиляция** — по желанию пользователя для серии из нескольких
   загруженных томов: предпросмотр (порядок томов, итоговое название,
   оглавление, размер, скачать собранный файл), галочка «собрать в один
   файл». **Тома заменяются сборником.** Собираются только тома самого
   пользователя (компилятор уже группирует по набору владельцев — этап 1).
7. **Одобрения суперпользователем нет** — он сам решает, открывать ли свою
   библиотеку всем.

### Конфиденциальность: пользователь не должен узнать о чужих книгах
Пользователь считает библиотеку своей; ни таблица, ни сообщения, ни его
каталог не должны выдавать, что в общем дереве лежат чужие книги.
- **Дилогия суперпользователя + 3-й том от пользователя** — трилогией не
  становится ни при загрузке, ни при запуске компилятора суперпользователем
  (разные владельцы — разные группы). Иначе пользователь получил бы тома
  1–2, которых не загружал. У пользователя — серия из тома №3; у
  суперпользователя его дилогия не меняется.
- **Дубли.** «Уже есть в библиотеке» — только если книга видна самому
  пользователю. Есть только у других — молча: пользователь становится
  совладельцем того же файла (без копии). Но если он правил в таблице
  автора/название/серию — общий файл не трогать (это изменило бы чужую
  книгу), а положить отдельную копию.
- **Совпадение имени файла** при синхронизации — решается молча, без
  сообщений «файл уже существует».
- **Подсказки** авторов и серий — только из видимого пользователю (п. 4).
- **Квота** — совместно используемый файл засчитывается пользователю
  целиком (для него это его книга).

## Риски
- **Перенос владения пропущен в какой-то операции** → книга «теряет»
  владельца → по правилу становится администраторской (не утечка, а
  пропажа у пользователя). Ловится сверкой (`library_owners_check`) и
  отпечатками `library_memory`.
- **Забытый фильтр в новом адресе** → утечка. Ловится тестом полноты.
- **Производительность** `Exists`-подзапросов на SQLite при ~7 тыс. книг —
  проверить на реальной базе на шаге 1.5 (индексы `BookOwner`).
- **Два корня** (`library_path` ≠ `root_lib`) — соглашение 0.
