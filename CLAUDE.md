# sopds-modern

Django 5.2 веб-приложение: OPDS-каталог электронных книг (SOPDS) +
инструмент организации FB2-библиотеки (fb2parser), в одном репозитории.

## Стек и структура

- Django 5.2, Python 3.13, SQLite (WAL). htmx + Foundation 6 на фронте.
- `src/sopds/settings/` — настройки (`base.py`, `local.py` — dev, LocMemCache).
- `src/opds_catalog/` — модели SOPDS, сканер (`sopdscan.py`), OPDS-фиды.
- `src/sopds_web_backend/` — основной SOPDS web UI (`/web/`).
- `src/fb2parser_core/` — логика организации библиотеки: 6-пасовый
  пайплайн определения автора/серии/жанра (`regen_csv.py` + `passes/`),
  компилятор многотомных серий в один файл (`fb2_compiler.py`),
  синхронизация в библиотеку (`synchronization.py`).
- `src/fb2parser_web/` — Django web-UI для fb2parser_core (`/fb2parser/`).
- `src/book_tools/` — парсеры FB2/EPUB/MOBI.
- `src/fb2_data/` — пользовательские данные: CSV, `settings/app_settings.json`,
  `genres.xml`.

**Важно:** fb2parser полностью вендорен в этом репозитории
(`fb2parser_core`/`fb2parser_web`) — это НЕ мост к внешнему проекту.
Старый standalone Tkinter-инструмент (когда-то был по пути
`c:\Temp\fb2parser`) устарел и не связан с текущим кодом.

## regen_csv / fb2_compiler — регрессионные фикстуры

`fb2parser_core`'s пайплайн определения автора/серии/жанра — эвристический
и легко ломается на новых структурах папок. Каждый разобранный краевой
случай должен закрепляться тестом:
`tests/integration/fb2parser_core/` — см. **README.md там** за полным
процессом (как добавить новый кейс через `scripts/build_regen_fixtures.py`).
Запуск: `python -m pytest tests/integration/fb2parser_core/` (настройки по
умолчанию — `sopds.settings.test`, как в CI; весь набор — `python -m pytest`).

## Обязательные конвенции

**i18n.** Любой новый UI-текст в шаблонах (`sopds_web_backend/templates/`,
`fb2parser_web/templates/`) — обязательно в `{% trans %}`/`{% blocktrans %}`,
плюс перевод в `locale/ru/LC_MESSAGES/django.po` соответствующего приложения.
Компиляция `.mo`: `python src/compile_messages.py` (не `manage.py
compilemessages` — `msgfmt` может отсутствовать в системе, скрипт
использует `polib`). Исключение: технические имена колонок CSV/полей
(`file_path`, `series_source` и т.п. в таблицах normalize.html) — всегда
на английском, не оборачиваются в `{% trans %}`.

**Выбор папки.** Любое текстовое поле ввода пути к папке в `/fb2parser/`
обязано иметь рядом кнопку «Обзор»/«📁» (htmx-запрос к
`/fb2parser/browse/?path=...`).

**Видимость книг (многопользовательская библиотека).** Пользователь видит
только свои книги, открытые ему и открытые всем; суперпользователь — всё
(`docs/multiuser-design.md`).
- Любая выдача книг, авторов, серий, жанров, папок, счётчиков (OPDS, сайт,
  Telegram) — через `opds_catalog/visibility.py` (`visible_books`,
  `restrict_books`, `visible_authors/series/genres`, `visible_book_count`,
  `get_visible_book_or_404`), сервисы каталога — с обязательным `user`.
  Чужая книга по id — 404, как несуществующая.
- Новый адрес в `opds`/`web` — тест изоляции в `tests/integration/access/`
  и строка в `test_url_coverage.py` (иначе он падает).
- Объекты OPDS-фидов общие для всех запросов и потоков: ничего, что
  относится к запросу, не хранить в `self` — только в `obj` и элементах.
- Любая операция, которая кладёт файл в библиотеку, двигает, сливает или
  удаляет его, — сообщает об этом через `fb2parser_core/ownership_hooks.py`
  (`assign`/`transfer`/`merge`/`release`); владение меняется только через
  `opds_catalog/ownership.py`. Расхождения — `manage.py library_owners_check`.

**Роли.** Ролей две: «Пользователь» и «Суперпользователь» (`is_superuser`
+ `is_staff` — второй флаг нужен fb2parser и `/admin/`; ставятся вместе).
«admin» — только имя учётной записи, не роль: в интерфейсе, текстах и
переводах роль называется «суперпользователь» (не «Admin»,
не «администратор»). Проверки прав — по `is_superuser` (`sopds_admin`,
`visibility.is_library_admin`, код входа, `superuser_required` в fb2parser,
`admin.site.has_permission`) — не по `is_staff`.

**Безопасность учётной записи** (`tests/integration/sopds_web_backend/test_account_security.py`).
- Действие, дающее долговременный доступ к аккаунту (пароль для читалок,
  привязка Telegram, приложение второго фактора и т. п.), — только с
  подтверждением паролем (`_PASSWORD_CONFIRMED_ACTIONS` в views.py).
- Смена пароля (`_after_password_change`) отзывает такие способы входа:
  новый способ — добавить туда же.
- Проверка кода второго фактора где угодно — через счётчик неверных кодов
  на аккаунт (`login_codes.note_failure`/`account_locked`).
- Пароли (`sopds_web_backend/password_rules.py`, тесты —
  `test_password_policy.py`): суперпользователь — от 12 символов,
  пользователь — от 8; строчная и заглавная латинская буква, цифра,
  спецсимвол; буквы только латинские. Новый способ задать пароль — через
  `validate_password` с пользователем уже в той роли, которую он получит, и
  с кнопкой генератора (`static/js/password-generator.js`). Пароль, заданный
  суперпользователем за другого, — временный (`set_must_change(user, True)`):
  при входе — обязательная смена (`PasswordChangeRequiredMiddleware`).
- Режим «На реконструкции» (`sopds_web_backend/maintenance.py`): любой
  адрес закрыт для всех, кроме суперпользователя на сайте; OPDS и бот — для
  всех. Открыть адрес во время ремонта — только добавив его в
  `maintenance.ALLOWED` с причиной; обход всех адресов —
  `tests/integration/access/test_maintenance.py`.
- Данные из книг (название, аннотация и т. п.) и имена пользователей в
  HTML — только экранированными; имена других пользователей — только
  суперпользователю. Исключения в текстах: права в
Telegram («добавьте бота администратором канала») и человек,
обслуживающий сервер.

## Обновление проекта («обнови проект»)

1. `git fetch origin && git log HEAD..origin/master --oneline`
2. `git merge origin/master` (не rebase)
3. `python manage.py migrate`
4. `python compile_messages.py`
5. `python manage.py check`
6. Если менялся `pyproject.toml`/`uv.lock` — `uv sync` (или `pip install`
   недостающих пакетов вручную, если `uv` недоступен в шелле)

## Версии и выпуски

Формат — `vX.YY.ZZZ` (на сайте: «SOPDS-MODERN v2.27.001»). Единственный
источник — `version` в `pyproject.toml`, без ведущих нулей (PEP 440:
`2.27.1`); показ с нулями — `src/sopds/version.py`. `SOPDS_VERSION` в
`.env` не используется. Тег выпуска — `vX.YY.ZZZ`.

**Что меняет какой разряд** (младшие разряды при этом обнуляются):
- **X** — обновление требует ручных действий от того, кто обслуживает
  сервер, или без них что-то перестанет работать: новая обязательная
  программа (как memcached), перенос настроек или данных без миграции,
  переписанная история git, смена версии Python, удаление функции, на
  которую полагались. Коммит — `feat!:`/`fix!:` или строка
  `BREAKING: <что сделать на сервере>` в тексте.
- **YY** — новая видимая возможность (`feat:`): страница, настройка,
  функция, миграция с новой функцией. Изменение, которое требует действий
  только от части пользователей (как «читалки со 2ФА — только пароль для
  читалок»), — тоже YY, с записью в «⚠ Внимание» в `CHANGELOG.md`.
- **ZZZ** — исправление: `fix:`, `security:`, `perf:`, `data:` (общие
  данные `genres.xml`/`app_settings.json` меняют поведение fb2parser).
- **Не меняют номер** — `docs:`, `test:`, `ci:`, `chore:`, `style:`,
  `refactor:` без видимого эффекта.

**Номер меняется на выпуск, не на коммит.** Выпуск — обновление сервера;
номер растёт по самому значимому изменению с прошлого тега (несколько
коммитов одной функции — одна новая версия). Поэтому тип коммита в начале
сообщения обязателен, а несовместимое изменение — помечено.

**Порядок выпуска** (перед каждым обновлением сервера):
1. `python scripts/version.py next` — показать пользователю предлагаемый
   номер и какие коммиты на него повлияли; X — только с его согласия.
2. `python scripts/version.py release` — `pyproject.toml`, `uv.lock`,
   раздел в `CHANGELOG.md` (проверить и поправить текст раздела: он
   собирается из сообщений коммитов).
3. Коммит выпуска (с подтверждением пользователя), затем
   `python scripts/version.py tag`, `git push origin master` и
   `git push origin vX.YY.ZZZ`.
4. Обновление сервера. Сначала — `git status` на сервере: суперпользователь
   правит общие данные прямо там (fb2parser: «Объединить» псевдоним в
   «Дублях серий», замены имён, жанры), и изменённый
   `src/fb2_data/settings/app_settings.json` / `genres.xml` остановит
   `git merge --ff-only`. Такие изменения сначала забрать в репозиторий
   отдельным `data:`-коммитом (слить с локальными), потом обновлять.

История до `v2.27.001` восстановлена по коммитам (`CHANGELOG.md`,
«История версий»): `v0.01.000` — начало sopds-modern (2025-07-13),
`v1.00.000` — 2026-07-14, `v2.00.000` — 2026-10-02. Старые теги
(`v0.42`…`v0.50`, `1.0.0RC1`) не трогать.

## Git-дисциплина

- Никогда `git add -A` — стейджить конкретные файлы.
- Коммитить только по явному подтверждению пользователя.
- `git fetch origin` + проверка расхождения перед каждым push.
- Коммит-сообщения заканчиваются `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`.
- `src/fb2_data/settings/app_settings.json` и `src/fb2_data/genres.xml` —
  общие данные, коммитятся и пушатся как обычные файлы (не исключать
  их из `git add` по умолчанию).
- `src/fb2_data/settings/config.json` — всегда только локальный
  (в `.gitignore`), содержит исключительно локальные настройки машины —
  никогда не коммитить и не пушить.
