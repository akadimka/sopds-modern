# regen_csv / fb2_compiler regression fixtures

`test_regen_edge_cases.py` защищает `fb2parser_core.regen_csv` и
`fb2parser_core.fb2_compiler` от повторных регрессий на реальных
"хитрых" структурах папок — без ручного full-library прогона (который
занимает 10+ минут: полный скан + git stash + повторный скан + diff).

## Как это устроено

- `tests/data/regen_library/` — облегчённый набор реальных папок из
  библиотеки пользователя. Имена файлов/папок и FB2-метаданные
  (author/title/sequence/genre) настоящие; текст книги (`<body>`) и
  обложки (`<binary>`) вырезаны и заменены короткими заглушками — в
  репозиторий не должен попадать авторский контент.
- `scripts/build_regen_fixtures.py` — скрипт, который это строит.
  `SOURCES` в нём — список (папка, лимит файлов, рекурсивно ли).
- `test_regen_edge_cases.py` — один тестовый класс на один разобранный
  баг, с прямыми assert на конкретное ожидаемое поведение (не общий
  snapshot-diff).

## Когда пополнять

**Каждый раз**, когда в этой сессии (или следующей) находится и
чинится новый краевой случай в regen_csv/fb2_compiler на реальных
данных пользователя — он должен попасть сюда. Не откладывать "на
потом": если фикс не закреплён тестом, in следующий раз при похожем
изменении регрессия пройдёт незамеченной.

## Процесс добавления нового кейса

1. Нашли и почини́ли баг на конкретной реальной папке.
2. Открыть `scripts/build_regen_fixtures.py`, добавить в `SOURCES`
   кортеж `(относительный_путь_папки, лимит_или_None, recursive)`.
   - `recursive=True` — если внутри есть вложенные подпапки-подсерии,
     которые важны для кейса (как у Эльтеррус/Отзвуки, Бессонов/Мир
     Алекса Королёва).
   - `лимит` — если папка большая и не вся нужна для теста (например,
     "Роберт Дж. Сойер" — плоская папка с полусотней файлов, для теста
     достаточно 15).
3. Прогнать:
   ```
   python scripts/build_regen_fixtures.py "<путь_к_реальной_библиотеке>"
   ```
   Скрипт полностью пересобирает `tests/data/regen_library/` с нуля из
   ВСЕХ записей в `SOURCES` — то есть каждый раз нужен доступ к
   исходной библиотеке (обычно `C:\Users\dmitriy.murov\Downloads\
   TriblerDownloads\Test1` или аналог), а не только к новой папке.
4. Добавить новый `class Test...` в `test_regen_edge_cases.py` —
   с докстрингом, ЧТО именно это проверяет и в чём была ошибка, плюс
   точечный assert (см. существующие классы как образец).
5. Прогнать:
   ```
   DJANGO_SETTINGS_MODULE=sopds.settings.local python -m pytest tests/integration/fb2parser_core/ -v
   ```
6. Если баг найден, но **не почини́лся** сразу (решили отложить) —
   всё равно можно добавить тест как `@pytest.mark.xfail(reason="...", strict=True)`,
   чтобы не забыть и не дать будущему фиксу тихо пройти мимо (см.
   `TestSmolinZeroPaddedPrefix` — обнаружен, но пока не исправлен ноль
   в ведущем номере файла).

## Тесты компилятора с контролируемым размером файлов

`test_compile_completeness.py` + `tests/data/compile_completeness/` +
`scripts/build_compile_completeness_fixture.py` — отдельный, полностью
СИНТЕТИЧЕСКИЙ (не из реальной библиотеки) fixture-набор для случаев,
где сам РАЗМЕР файла на диске имеет значение для проверки (например,
"выбор лучшей предкомпиляции не должен ориентироваться только на
ширину диапазона томов, есть же ещё размер файла"). Реальные файлы для
таких кейсов брать не с руки — соотношение размеров пришлось бы
подгонять, а тут можно просто сгенерировать текст нужной длины. Тот же
принцип: один тестовый файл-паттерн на один разобранный баг, скрипт
воспроизводим, никакого реального книжного контента.

## Важно: это НЕ полная копия библиотеки

Цель — компактный набор показательных мини-кейсов (сотни КБ), а не вся
пользовательская библиотека. Даже если у пользователя 80 тысяч файлов —
в `tests/data/regen_library/` должны попадать только те конкретные
папки, на которых нашли и разобрали баг, а не весь массив целиком.
Полный анализ большой библиотеки — отдельная задача (найти новые
проблемы), результат которой (конкретные папки) уже потом добавляется
сюда по этому же процессу.
